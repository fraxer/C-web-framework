# 00 — Конкурентное исполнение хендлеров на одном соединении

Отдельный план, выделенный из фазы 4 HTTP/2 (`docs/http2/07-roadmap-testing.md`).
Задача не относится к h2-слою: ограничение живёт в модели блокировок соединения
и одинаково действует на HTTP/1.1, HTTP/2 и WebSocket.

Все ссылки `file:line` проверены по коду на момент написания (после коммита
`e4a7eae`, мультиплексирование h2).

---

## 1. Что ограничено сегодня

Хендлеры **одного соединения** исполняются строго по одному. Хендлеры разных
соединений идут параллельно — этот случай работает и не меняется.

До фазы 4 HTTP/2 это не проявлялось: в h1.1 на соединении и так один запрос
за раз, в h2 был один поток. С мультиплексированием на соединении может висеть
до `H2_MAX_CONCURRENT_STREAMS` (сейчас 100) запросов, и они выстраиваются в
очередь, даже когда свободны все воркер-потоки.

Цена: один медленный хендлер (запрос в БД, обращение по HTTP-клиенту, чтение
файла) задерживает все остальные потоки того же соединения. Для браузера,
который открывает одно h2-соединение на домен, это означает, что параллелизм
запросов на странице определяется не пулом воркеров, а самым медленным
хендлером.

---

## 2. Откуда берётся ограничение (аудит)

### 2.1 Лок берётся до вызова хендлера и держится всё время

`connection_queue_guard_pop()` (`src/connection/connection_queue.c:47`)
возвращает соединение **с уже захваченным** `connection_s_lock`:

```c
connection_t* __connection_queue_pop() {
    connection_t* connection = cqueue_pop(queue);
    ...
    connection_s_lock(connection);      // ← захват
    ...
    return connection;                  // отдаётся залоченным
}
```

`thread_handler` (`src/thread/threadhandler.c:23-48`) держит его до конца
итерации:

```c
connection_t* connection = connection_queue_guard_pop();  // already locked
...
item->run(item);                        // ← весь хендлер под локом
item->free(item);
if (connection_s_dec(connection) == CONNECTION_DEC_RESULT_DECREMENT)
    connection_s_unlock(connection);
```

`item->run` для HTTP — это `__queue_request_handler`
(`protocols/http/server/httpserverhandlers.c`), внутри которого
`run_middlewares(...)` и `item->handle(&ctx)` — произвольный код из
пользовательского `.so`: запросы в БД, файловый ввод-вывод, HTTP-клиент, SMTP.
Для WebSocket — `websockets_queue_request_handler`
(`protocols/websocket/server/websocketsserverhandlers.c`), устроенный так же.

### 2.2 Лок — спинлок без уступки процессора

`connection_s_lock` (`src/connection/connection_s.c:114-127`) — голый CAS-цикл:

```c
do { expected = 0; }
while (!atomic_compare_exchange_strong(&ctx->locked, &expected, desired));
```

Ни `sched_yield`, ни backoff. Ждущий поток сжигает ядро.

### 2.3 Почему это сегодня не жжёт CPU

Потому что пока хендлер работает, соединение выведено из epoll:
`connection_queue_append` (`src/connection/connection_s.c:217`) ставит
`MPXONESHOT`, и воркер просто не получает событий по этому fd. Спорить за лок
некому.

> Это важное свойство: оно означает, что нынешняя схема **корректна**, а не
> «случайно работает». Менять её нужно осознанно, а не потому, что она плохая.

### 2.4 Кто ещё берёт этот лок

| Кто | Где |
|---|---|
| read/write guard'ы HTTP/1.1 | `httpserverhandlers.c:91,104` |
| read/write guard'ы HTTP/2 | `h2session.c:1255,1265` |
| read/write guard'ы WebSocket | `websocketsserverhandlers.c:35,43` |
| `connection_close` | `connection_s.c:247` |
| `__listener_connection_close` | `multiplexingserver.c:68` |
| поток-обработчик | `connection_queue.c:47` (через pop) |

### 2.5 Второй механизм сериализации: одна заявка на соединение

Лок — не единственная причина. Даже если отпустить его полностью, параллелизма
не появится: **соединение стоит в глобальной очереди максимум в одном
экземпляре, и с него снимается ровно один item за одну выемку.**

- `connection_queue_append` (`src/connection/connection_s.c:225-228`) делает CAS
  `broadcast_ref_count 1→2` и при неудаче возвращает *успех*: повторная
  постановка уже припаркованного соединения — no-op.

  ```c
  int expected = 1;
  if (!atomic_compare_exchange_strong(&ctx->broadcast_ref_count, &expected, 2))
      return 1;                      // ← уже в очереди, ничего не делаем
  ```

- `__deferred_handler` (`protocols/http/server/httpserverhandlers.c:338-348`)
  кладёт item в `ctx->queue`, но зовёт `connection_queue_append` **только если
  очередь была пуста**;
- `thread_handler` (`src/thread/threadhandler.c:29-45`) снимает с `ctx->queue`
  **один** item и после него отдаёт соединение;
- ход следующему item'у даёт `h2_server_response_ready`
  (`protocols/http2/server/h2session.c:1583-1586`) — она перевешивает соединение
  обратно в очередь **после** того, как хендлер вернулся.

Получается цепочка, а не веер. Это ровно та подпись, что видна в замере §7.1:
интервалы стык-в-стык, `tid` разные — работу разбирают разные воркеры, но по
очереди, потому что заявка в каждый момент одна.

> **Следствие для §5:** сужение критической секции само по себе не
> распараллеливает ничего. Второй воркер не придёт за вторым потоком h2, пока
> соединение не окажется в глобальной очереди второй раз. Нужен парный шаг —
> веерная раздача (§5.1).

Рефсчёт к такой раздаче уже готов: каждый append делает `connection_s_inc`
(`connection_queue.c:99`), каждый воркер — `connection_s_dec`
(`threadhandler.c:47`). А вот связка `dec`/`unlock` в `thread_handler` — нет,
см. §4.7.

## 3. Почему это НЕ «переписать модель блокировок»

Ключевое наблюдение: **хендлеры уже сейчас исполняются параллельно на разных
соединениях.** Значит, всё общее состояние фреймворка уже обязано быть
потокобезопасным, и оно такое:

- ratelimiter — собственный спинлок + seqlock (`ratelimiter.c:13-36`);
- пул соединений БД — атомарные CAS-локи (`database/database.c:95-115`);
- broadcast-очереди — `cqueue_lock` (`broadcast.c`);
- storage / view / translation / session — вызываются из хендлеров разных
  соединений одновременно уже сегодня.

Отсюда: снятие сериализации **не добавляет новой глобальной конкурентности.**
Оно добавляет конкурентность ровно внутри одного соединения. Значит, область
аудита — перечислимый список: состояние `connection_server_ctx_t`, состояние
протокольной сессии (h2session/h2stream, wsparser) и объекты
запроса/ответа.

Это и делает задачу отдельным, обозримым планом, а не бессрочным рефактором.

## 4. Что сломается, если просто отпустить лок

Перечень найденных гонок — это и есть содержание работы.

### 4.1 Битовые поля в общем слове

`connection_server_ctx_t` (`src/connection/connection_s.h:53-58`):

```c
unsigned need_write: 1;
unsigned is_http2: 1;
```

Оба лежат в одном машинном слове. Запись в `need_write` из потока-обработчика
(через `h2_server_response_ready`) параллельно с чтением/записью из воркера —
read-modify-write по общему слову, то есть гонка данных по стандарту C, а не
«теоретическая». То же самое в `h2stream_t` (`h2stream.h`): `handler_pending`,
`response_ready`, `cancelled`, `end_stream_sent`, `window_blocked` — все в
одном слове, и пишутся с обеих сторон.

**Что делать:** развести на отдельные `_Atomic`-поля (или на отдельные байты)
те флаги, что пересекают границу потоков. Остальные оставить битовыми — они
касаются только воркера.

### 4.2 Публикация ответа должна быть release/acquire

Хендлер заполняет `httpresponse_t` (тело, заголовки), затем выставляет
`stream->response_ready`. Воркер, увидев флаг, читает тело. Без
release-store / acquire-load воркер вправе увидеть флаг раньше содержимого.
Сейчас это прикрыто локом; после его снятия нужна явная синхронизация.

### 4.3 Жизненный цикл потока и соединения

Здесь всё уже подготовлено фазой 4:

- время жизни **соединения** держит `ctx->ref_count`
  (`connection_s_inc` при постановке в очередь) — лок за это не отвечает;
- время жизни **потока h2** прикрыто `handler_pending`/`cancelled`
  (`h2stream_close`): пришедший RST_STREAM не сносит поток, пока хендлер держит
  его request/response.

Оба механизма писались именно под этот случай и должны пережить снятие лока —
но их нужно перепроверить уже как настоящие межпоточные, а не как защиту от
переиспользования внутри одного потока.

### 4.4 `conn_ctx->request/response` у h1.1 и WebSocket — ✅ решено (фаза C)

`websockets_queue_request_handler` клал ответ в `conn_ctx->response`
(`websocketsserverhandlers.c`), h1.1 — в `__queue_request_handler`. Пока на
соединении один запрос за раз, это безопасно; при конкурентных хендлерах
WebSocket-сообщений — уже нет. h2 от этой пары отвязан фазой 4.

Решение для WebSocket — очередь вывода `ctx->write_queue` из слотов
`connection_out_slot_t` (`connection_s.h`): слот резервируется при диспетче,
заполняется при завершении хендлера, путь записи снимает только заполненную
голову. `conn_ctx->response` остался «ответом, который сейчас пишется».
Подробности и почему порядок вывода сохраняется — фаза C в §6.

h1.1 сознательно не тронут: у него один запрос в полёте по определению (§9).

### 4.5 Кто пишет в сокет — ✅ проверено (фаза A)

Инвариант: **в сокет пишет только воркер.** Аудит проведён, инвариант держится.

Точек записи ровно три, и все дублируют одну и ту же пару «SSL или send»:

| Функция | Файл | Откуда достижима |
|---|---|---|
| `connection_data_write` | `src/connection/connection.c:36` | путь чтения воркера (`h2_flush_out`) |
| `__write` | `protocols/http/server/filters/http_write_filter.c:13` | `__write` → `connection->write` (воркер) |
| `__raw_write` | `protocols/http2/server/h2_write_filter.c:46` | `h2_write` → `h2_server_guard_write` (воркер) |

Write-фильтры запускаются только из `__write`
(`httpserverhandlers.c:309,315`), а это `http_server_guard_write`, то есть
`connection->write`. Хендлерские пути заканчиваются на `__handler_finished` →
`connection_after_read`/`h2_server_response_ready`, где нет ничего кроме
`epoll_ctl`.

Проверены и два подозреваемых из исходной формулировки:

- **broadcast** — `__broadcast_queue_request_handler` (`broadcast.c:334`) только
  склеивает кадры в тело `websocketsresponse_t` и зовёт `connection_after_read`;
- **WebSocket** — `__post_response` (`websocketsserverhandlers.c:308`) ставит
  `ctx->response` + `need_write` и тоже уходит в `connection_after_read`.

Единственная запись из потока-обработчика — SMTP-клиент
(`protocols/smtp/mail.c:679,937,1013`), но он пишет в **своё клиентское**
соединение, которым не владеет ни один воркер. Вне области задачи.

Инвариант зафиксирован комментарием на `connection_data_write`
(`src/connection/connection.h`) с отсылками из обоих фильтров — чтобы
следующий, кто захочет писать из хендлера, наткнулся на него раньше, чем на
`SSL_write`.

### 4.6 `epoll_ctl` с двух сторон

`connection_after_read` вызывается из потока-обработчика и делает
`control_mod`. Воркер делает то же самое. Сам `epoll_ctl` потокобезопасен, но
логическое состояние («что сейчас взведено») может разъехаться. Нужен разбор:
кто имеет право взводить события и в какой момент. Частично это уже
происходит сегодня через broadcast, так что случай не новый.

### 4.7 Связка `connection_s_dec` / `connection_s_unlock` в `thread_handler`

```c
if (connection_s_dec(connection) == CONNECTION_DEC_RESULT_DECREMENT)
    connection_s_unlock(connection);     // threadhandler.c:47-48
```

Сегодня это корректно: соединение выдаётся ровно одному воркеру, взявшему лок в
`pop`, — «отпустить ссылку» и «отпустить лок» совпадают. При веерной раздаче
(§2.5) совпадение исчезает: соединение одновременно у нескольких воркеров, лок
берётся и отпускается точечно вокруг коротких секций, и `unlock` больше не
должен зависеть от результата `dec`. Разводить эти две операции — часть фазы B,
а не деталь реализации: пропущенный случай здесь даёт либо залипший спинлок,
либо unlock чужой критической секции.

### 4.8 Соединение глухое, пока работают хендлеры

`connection_queue_append` паркует fd через `control_mod(MPXONESHOT)`
(`connection_s.c:230`) — без `MPXIN`, то есть событий по сокету не будет вообще.
Пока хендлеры одного соединения работают, новые HEADERS **не читаются**: чтение
возобновляет только `connection_after_read` (`MPXOUT | MPXRDHUP`) на пути
готового ответа.

Для браузера с одним h2-соединением на домен это второй, независимый источник
задержки: даже полностью распараллелив уже разобранные потоки, мы не начнём
разбирать те, что пришли за время их работы.

**После фазы B ограничение частично снялось само:** первый же завершившийся
хендлер зовёт `connection_after_read`, соединение снова армируется, и воркер
читает новые HEADERS, пока остальные хендлеры ещё работают. Полностью вопрос
не закрыт — до первого завершения соединение по-прежнему глухое, — но это уже
не «N×T последовательных окон». Именно это возобновление чтения на фоне
работающих хендлеров и вскрыло два бага, описанных в фазе B.

Остаток вынесен в `01-lock-scope-io-paths.md`, фаза E — там же разобрано,
почему `MPXIN` возвращается только после **записи** первого ответа, а не после
возврата первого хендлера.

## 5. Предлагаемое решение

Решение состоит из двух парных шагов (§5.1 и §5.2). По отдельности ни один из
них не даёт параллелизма: первый убирает взаимное исключение, второй — очередь
из одной заявки. Нужны оба.

### 5.1 Сузить критическую секцию

Не убирать лок, а **сузить**: он остаётся защитой состояния соединения, но
перестаёт покрывать исполнение пользовательского кода.

```c
// __queue_request_handler, схематично
/* --- под локом: разбор item, ratelimiter, привязка ctx --- */
connection_s_unlock(connection);

run_middlewares(...);
item->handle(&ctx);              // ← пользовательский код, без лока

connection_s_lock(connection);
/* --- под локом: публикация ответа, дренаж очереди, re-arm --- */
```

Почему так, а не «убрать лок совсем»:

- сохраняется дешевизна спинлока — он снова держится микросекунды, для чего
  спинлоки и предназначены;
- состояние соединения остаётся под явной защитой: снимается сериализация
  пользовательского кода, а не инварианты `connection_server_ctx_t`;
- изменение локализовано в двух runner'ах (HTTP и WebSocket), а не размазано
  по всему стеку.

Контракт `thread_handler` при этом всё же меняется: `connection_s_unlock`
перестаёт быть следствием `connection_s_dec` — см. §4.7.

### 5.2 Веерная раздача соединения

Снять ограничение «одна заявка на соединение» из §2.5: при выемке item'а, если
`ctx->queue` не пуста, сразу перевесить соединение обратно в глобальную очередь
— **до** запуска хендлера, а не после его возврата.

```c
// thread_handler, схематично
connection_queue_item_t* item = cqueue_pop(ctx->queue);

if (!cqueue_empty(ctx->queue))
    connection_queue_guard_append(connection);   // ← следующий воркер идёт сюда же

item->run(item);                                 // ← уже без лока (§5.1)
```

Тогда N разобранных за одно чтение потоков h2 расходятся по N воркерам, а не
выстраиваются в цепочку через `h2_server_response_ready`. Что нужно проверить
при этом:

- гард `broadcast_ref_count` разведён на две роли: «fd припаркован» (CAS `1→2`,
  ровно один `epoll_ctl` на соединение — вынесен в `__park`) и «есть заявка»
  (по одной на каждый item). Раньше это была одна проверка, и именно она
  ограничивала соединение одной заявкой;
- `connection_after_write` по-прежнему сбрасывает `broadcast_ref_count` CAS
  `2→1`, распарковывая соединение. При веере этот сброс перестаёт быть
  «последним» — но он и не обязан им быть: следующий `__park` просто
  припаркует заново;
- цепочка в `h2_server_response_ready` после этого избыточна и снята: каждый
  item уже имеет собственную заявку, а лишняя постановка стоила бы холостой
  выемки.

Отдельным (и, возможно, первым) шагом стоит заменить голый CAS-цикл на
спинлок с `sched_yield`/паузой: даже при узкой секции это страховка от
патологического сжигания ядра, и это изменение полезно само по себе,
безотносительно конкурентности.

## 6. Фазы

### Фаза A — Подготовка (безопасно, без изменения поведения) — ✅ сделано

1. ✅ Спинлок с backoff в `connection_s_lock` (`connection_s.c`): CAS-цикл
   заменён на «CAS → спин на relaxed-load с `PAUSE` → `sched_yield` после 128
   итераций». Повторный `atomic_load` перед следующим CAS важен не меньше
   yield'а: CAS пишет в кэш-линию даже при неудаче, и толпа ждущих гоняла бы
   линию между ядрами, тормозя держателя.
2. ✅ Межпоточные флаги разведены:
   - `ctx->need_write` → `atomic_bool` (release на записи, acquire на чтении).
     Это была **уже существующая гонка**, а не задел на будущее: воркер читает
     флаг в `multiplexingepoll.c` вне `connection_s_lock`, а пишет его
     поток-обработчик;
   - `handler_pending` / `response_ready` / `cancelled` в `h2stream_t` →
     `atomic_bool`, остальные флаги остались битовыми (их касается только
     воркер);
   - публикация ответа (§4.2) оформлена парой release-store в
     `h2_server_response_ready` / acquire-load в `h2_has_writable` и в проходе
     записи;
   - `is_http2` осознанно оставлен битовым полем: он пишется однократно до
     того, как на соединении может запуститься первый хендлер. Обоснование

#### Что фаза B вскрыла (оба бага — настоящие, оба чинились здесь же)

**1. Событийный пакет epoll держит сырые указатели.**
`__mpx_epoll_process_events` разбирает пакет `epoll_wait` по одному событию, а
`__mpx_on_tick` внутри того же пакета обходит весь список соединений воркера и
может закрыть **другое** соединение из этого же пакета. Закрытие отпускает
базовую ссылку; если хендлер на другом ядре в этот момент отпускает последнюю —
соединение освобождается, и остаток массива событий висячий. Пока хендлеры были
сериализованы, это было недостижимо: соединение с работой в очереди выведено из
epoll и не могло попасть в пакет. Починка: воркер пиннит ссылками все соединения
пакета до обработки первого события и отпускает их по одному.

**2. Перевзвод epoll после закрытия fd.**
Хендлер, закончив работу, зовёт `connection_after_read`/`rearm` — а воркер к
этому моменту мог уже закрыть соединение. `close(fd)` вернул номер дескриптора
ядру, следующий `accept()` его переиспользует, и `epoll_ctl(MOD)` попадает в
**чужую** регистрацию, подменяя ей `data.ptr` на почти освобождённый объект.
Дальше epoll отдаёт воркеру событие с висячим указателем — падение приходит из
`connection_s_inc`, а не из места ошибки. Починка: флаг
`connection_server_ctx_t::detached`, выставляемый под `connection_s_lock` сразу
после `control_del`, и проверка в обоих путях перевзвода. Отдельный от
`destroyed` флаг нужен потому, что `destroyed` ставят и на путях, где fd ещё
открыт и соединение должно быть добито событием.

**3. `ctx->server` читался из потока-обработчика (нашёл TSan).**
`httpparser_select_server` переписывает `ctx->server` на каждый запрос, а
runner читал его для `run_middlewares`. Это не только гонка: под h2 воркер
может успеть разобрать следующий запрос — возможно, с другим `:authority`, то
есть к другому vhost'у. Починка: vhost захватывается в данные item'а на момент
диспетча (`connection_queue_http_data_t::server`). Это ещё и исправление по
существу — middlewares должны браться от того сервера, которому принадлежит
сам запрос.

#### Почему порядок вывода сохранён (а не «как получится»)

В отличие от h2, у WebSocket нет идентификаторов потоков: клиент видит один
упорядоченный поток сообщений и сопоставляет ответы по позиции. Веер «кто
раньше закончил, тот раньше и ответил» тихо сломал бы любое приложение,
которое на это рассчитывает, — а рассчитывают почти все.

Поэтому распараллелено **исполнение**, а не **вывод**: слоты выстраиваются в
порядке диспетча, медленный хендлер задерживает только выдачу тех ответов, что
встали за ним, но не мешает им исполняться. Цена — head-of-line blocking на
записи; выигрыш — N×T → T без изменения контракта протокола.

#### Ограничение: permessage-deflate остаётся сериализованным

`ws_deflate` (RFC 7692) живёт на парсере — один `z_stream` на соединение — и
при context takeover сжимает все исходящие сообщения в одно скользящее окно.
Сжатие происходит внутри `send_*`, то есть в хендлере, а значит параллельные
хендлеры ломают и сам стрим (гонка), и его порядок (клиентский inflate
рассинхронизируется). Пока это так, соединения с согласованным
permessage-deflate идут по прежнему пути: `__fanout_allowed()` смотрит на
`parser->ws_deflate_enabled`, и при сжатии диспетч остаётся «одна заявка за
раз». Снять ограничение можно, перенеся кадрирование и сжатие в путь записи
(он упорядочен и однопоточен), — это отдельная работа, не входившая в фазу C.

Побочный эффект: сжатое соединение — это готовый «эталон до», измеримый на том
же бинарнике. Именно им получена колонка «Было» ниже.

#### Что фаза C попутно исправила

`__handle` не различал две причины нуля от `get_resource`: «нет маршрута» и
«диспетч отклонён». Во втором случае место в очереди вывода уже занято и
заполнить его некому, так что ответ «resource not found» встал бы за слотом,
который никто никогда не закроет, а соединение при этом жило бы дальше. Теперь
причины разводит `ctx->destroyed`, и отклонённый диспетч честно закрывает
соединение.

## 7. Как измерять эффект

Хендлер с управляемой задержкой добавлен: `app/routes/bench/bench.c`, функция
`delay`. Он спит `?ms=` миллисекунд (по умолчанию 200, потолок 10000) и
возвращает JSON с `started_ms`/`finished_ms` (CLOCK_MONOTONIC) и `tid`. Именно
эти поля, а не только общее время, различают два случая: при сериализации
интервалы `[started, finished]` непересекающиеся, при конкурентности —
наложенные. Маршрут `/delay` заведён в `config_h2c.json` на s1 (h2c, 18080) и
s2 (TLS, 18443).

Для фазы C есть ws-двойник: `app/routes/bench/wsbench.c`, тот же `delay` и те
же поля, маршрут `/wsdelay` на s3 (18081). Сообщение — `GET /wsdelay?ms=200&tag=a`
по resource-протоколу (клиент должен запросить `Sec-WebSocket-Protocol: resource`,
иначе соединение уйдёт на default-хендлер). Каналы рассылки заведены там же:
`/join`, `POST /send`, `/leave` — полезная нагрузка допускается только у
POST/PATCH (`websocketsrequest_has_payload`).

С фазы D к этому добавились счётчики (`/metrics`, см. §6): wall-clock отвечает
«стало ли быстрее», а `handlers.per_connection_max` — «идут ли хендлеры разом»,
и это разные вопросы. На быстрых хендлерах первый вопрос неразличим, а второй
по-прежнему даёт ответ, поэтому регрессию ловить надо им:

```bash
curl -s "http://127.0.0.1:18080/metrics?reset=1" > /dev/null   # окно открыто
nghttp -n "http://127.0.0.1:18080/delay?ms=200&tag=a" ...       # прогон
curl -s "http://127.0.0.1:18080/metrics" | jq .                 # окно закрыто
```

- **Базовый замер:** N запросов на одном h2-соединении к хендлеру с задержкой
  T. Сегодня ожидаемое общее время ≈ N×T; цель — ≈ T при N ≤ числу воркеров.
- **Регрессия:** те же прогоны на HTTP/1.1 не должны замедлиться.
- **TSan** — обязателен для этой задачи. Настроен в фазе A:

  ```bash
  mkdir build-tsan && cd build-tsan
  cmake .. -DCMAKE_BUILD_TYPE=Debug -DSANITIZE=thread -DBUILD_TESTS=yes \
           -DINCLUDE_POSTGRESQL=yes -DINCLUDE_MYSQL=yes \
           -DINCLUDE_REDIS=yes -DINCLUDE_SQLITE=yes
  cmake --build . -j$(nproc)

  TSAN_OPTIONS="halt_on_error=0" ./exec/runner        # unit-тесты
  TSAN_OPTIONS="halt_on_error=0" ./exec/cwfr -c ../config_h2c.json
  ```

  Пути к `.so` в `config_h2c.json` указывают на `build-debug/`, так что для
  TSan-сервера конфиг нужно скопировать с заменой на `build-tsan/` — иначе
  подгрузятся неинструментированные хендлеры и отчёты станут бессмысленными.
  `SANITIZE=thread` несовместим с ASan и отключает его; без опции всё как
  раньше (ASan+LSan на Debug/RelWithDebInfo).

### 7.1 Результат базового замера (2026-08-02, Debug/ASan, `workers: 2`, `threads: 4`)

```bash
# N потоков на ОДНОМ h2-соединении
nghttp -n "http://127.0.0.1:18080/delay?ms=200&tag=a" ... (N URL)

# N соединений — контрольный случай
for t in a b c d; do curl -s --http2-prior-knowledge ".../delay?ms=200&tag=$t" & done; wait
```

| Сценарий | N | T | Общее время | Ожидание |
|---|---|---|---|---|
| h2c, один conn, N потоков | 4 | 200 мс | **0,828 с** | N×T |
| h2c, один conn, N потоков | 8 | 200 мс | **1,620 с** | N×T |
| h2 over TLS, один conn | 4 | 200 мс | **0,821 с** | N×T |
| h2c, N **отдельных** соединений | 4 | 200 мс | **0,214 с** | T |
| HTTP/1.1, keep-alive, последовательно | 4 | 200 мс | **0,816 с** | N×T |

Интервалы исполнения на одном соединении стык-в-стык, без наложения:

```
{"tag":"a", started_ms:283746989.6, finished_ms:283747189.7, tid:2826089}
{"tag":"b", started_ms:283747189.8, finished_ms:283747389.8, tid:2826089}
{"tag":"c", started_ms:283747390.0, finished_ms:283747590.1, tid:2826092}
{"tag":"d", started_ms:283747591.2, finished_ms:283747791.3, tid:2826092}
```

**Вывод:** N×T воспроизводится ровно так, как предсказано в §1 — и на h2c, и на
h2 поверх TLS. Контрольный прогон по отдельным соединениям даёт ≈T с четырьмя
разными `tid`, то есть воркеров хватает, и упирается всё именно в сериализацию
по соединению, а не в пул потоков. Обратите внимание на `tid` в
одно-соединённом прогоне: потоки *разные* (2826089, 2826092) — работу
разбирают разные воркеры, но строго по очереди.

Именно разные `tid` и показывают, что причина не одна. Будь дело только в
`connection_s_lock`, ожидающий воркер крутился бы в CAS-цикле и подхватывал
работу сам; вместо этого он спит на `connection_queue_cond`, а соединение
приходит в очередь заново после каждого ответа. Это подпись пары «лок +
одна заявка на соединение» (§2.5) — и она же объясняет, почему §7.1 не жжёт CPU
(§2.3).

Задачу можно начинать с фазы A: ограничение измеримо и не является
теоретическим.

## 8. Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Пропущенная гонка в per-connection состоянии | высокая | критическое | TSan под нагрузкой; аудит по списку §4, а не «на глаз» |
| Хендлер пишет в сокет напрямую (не найденный путь) | средняя | критическое | §4.5 — проверка инварианта до, а не после |
| Разъезд состояния epoll при взводе с двух сторон | средняя | высокое | явный владелец re-arm; §4.6 |
| Регрессия HTTP/1.1 | низкая | критическое | h1.1 не выигрывает от изменения — можно оставить его сериализованным и не трогать вовсе |
| Спинлок под нагрузкой жжёт CPU | средняя | среднее | фаза A п.1 делается первой |
| Гард `broadcast_ref_count` рассчитан на одну выемку и разъедется при веере | высокая | высокое | §5.2 — пересмотр семантики гарда вместе с раздачей, не после |
| Залипший спинлок / unlock чужой секции после расцепления `dec`/`unlock` | средняя | критическое | §4.7 — отдельный пункт фазы B с ревизией всех путей `pop`→`unlock` |
| Сделан только один из парных шагов §5.1/§5.2 — «не работает, откатываем» | средняя | среднее | приёмка фазы B ставится один раз на оба шага; §2.5 объясняет почему |

## 9. Что НЕ входит

- Замена спинлока на мьютекс/futex по всему стеку — отдельный разговор.
- Пул воркеров, work stealing, привязка соединений к потокам.
- Приоритизация потоков h2 между собой (`docs/http2/07`, фаза 4).
- HTTP/1.1: выигрыша нет (один запрос за раз), поэтому его сериализацию можно
  сохранить как есть.
- Перенос кадрирования и сжатия WebSocket в путь записи. Это то, что сняло бы
  сериализацию со сжатых соединений (фаза C), но затрагивает весь
  `websocketsresponse` — отдельная задача.

## 10. Стоит ли делать

Честный ответ: **зависит от профиля нагрузки.**

Выигрыш появляется, когда на одном h2-соединении одновременно висят несколько
медленных (I/O-bound) хендлеров. Для статики и быстрых JSON-ответов текущей
сериализации хватает с запасом — там узкое место не в ней.

Поэтому перед фазой A имеет смысл сделать замер из §7 на реальном приложении:
если N×T не проявляется, задачу можно отложить, не потеряв ничего.

**Замер сделан (§7.1): N×T проявляется в чистом виде.** 8 медленных запросов на
одном h2-соединении — 1,62 с вместо 0,2 с при свободных воркерах. Так что
условие «зависит от профиля нагрузки» разрешается так: если в приложении есть
I/O-bound хендлеры и браузерные клиенты (одно h2-соединение на домен) —
выигрыш реальный и составляет до N-кратного по времени страницы. Если весь
трафик — статика и быстрые JSON, задача по-прежнему не приоритетна.
