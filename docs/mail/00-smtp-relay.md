# 00 — Отправка через SMTP-релей с аутентификацией

> Статус: **выполнено** (2026-09-08). Все пункты S.1–S.7 и D.1 закрыты;
> хроника и что именно проверено — в §13 в конце документа.
> Основание — перевод сайта synecta.tech с Django на cwfr (сентябрь 2026).
> Прежняя реализация отправляла почту через `smtp.mail.ru:587` с логином и
> паролем; cwfr так не умеет и доставляет письма только напрямую на MX
> получателя. Для сайта это означает, что вместо одной строки с учётными
> данными нужны PTR, SPF и DKIM, а письмо с непрогретого IP уходит в спам —
> что и произошло при первом же тесте (`550 spam message rejected` от mail.ru).

Документ описывает **второй режим доставки**, а не замену существующего. Прямая
доставка на MX остаётся тем, что делает `send_mail()` по умолчанию: она не
требует внешнего сервиса и уместна там, где домен и адрес уже с хорошей
репутацией. Релей нужен там, где такой репутации нет и заводить её ради формы
обратной связи незачем.

приложения. Это условие, а не пожелание: приложения, уже написанные под прямую
доставку, не должны замечать появления релея.

## 2. Что мешает сегодня

Полный путь отправки — `send_mail()` (`protocols/smtp/mail.c:129`):

```
mail_is_real(to)        MX домена получателя обязаны существовать
  -> connect(to)        __mail_connect: MX-резолв, connect на порт 25
  -> read_banner
  -> send_hello         EHLO env()->mail.host
  -> start_tls          STARTTLS обязателен
  -> MAIL FROM / RCPT TO / DATA / content
```

Пять мест, каждое из которых сейчас предполагает прямую доставку:

1. **`mail_is_real()`** (`mail.c:104`) вызывается безусловно и требует MX у
   домена **получателя**. При отправке через релей это лишняя внешняя
   зависимость: у внутреннего домена MX может не быть вовсе, а доставку всё
   равно выполняет релей.
2. **`__mail_connect()`** (`mail.c:281`) умеет ровно одно — вывести адрес из
   `payload->to` и резолвить его MX. Адреса релея взять неоткуда.
3. **Порт 25 зашит** в `__mail_connection_create()` (`mail.c:378`):
   `connection_c_create(fd, NULL, 25)`. Submission — это 587 или 465.
4. **AUTH нет вообще.** Ни команды, ни полей конфигурации, ни места, где их
   можно было бы взять.
5. **`smtpresponse_t`** (`protocols/smtp/smtpresponse.h`) хранит только `status`
   и текст последней строки. Список расширений из многострочного ответа на EHLO
   (`250-AUTH PLAIN LOGIN`) не разбирается — то есть неоткуда узнать, какой
   механизм аутентификации предлагает сервер.

Отдельно: `__mail_connect()` работает исключительно с IPv4 —
`connection_c_create(AF_INET)`, `struct sockaddr_in`, `struct in_addr ip_list[]`
в `mail_mx_record_t`. Релей по IPv6-адресу подключить будет нечем.

## 3. S.1 — Конфигурация

Релей описывается вложенным объектом в существующей секции `mail`. Его наличие и
есть переключатель режима: есть `relay` — письма идут через него, нет — прямая
доставка, как сейчас.

```json
"mail": {
    "host": "synecta.tech",
    "relay": {
        "host": "smtp.mail.ru",
        "port": 587,
        "security": "starttls",
        "user": "info@synecta.tech",
        "password": "...",
        "auth": "auto",
        "timeout": 15
    }
}
```

| Поле | Обязательное | Значение по умолчанию | Описание |
|------|--------------|----------------------|----------|
| `host` | **да** | — | Имя или адрес сервера-релея |
| `port` | нет | по `security`: 587 / 465 / 25 | Порт |
| `security` | нет | `starttls` | `starttls`, `tls` (implicit), `none` |
| `user` | нет | — | Логин; без него AUTH не выполняется |
| `password` | нет | — | Пароль |
| `auth` | нет | `auto` | `auto`, `plain`, `login`, `none` |
| `timeout` | нет | текущее значение сокета | Таймаут операций, сек |

Разбор — рядом с существующим чтением `dkim_*` в
`module_loader_config_load()` (`src/moduleloader/moduleloader.c:683`), хранение —
новая структура `env_mail_relay_t` внутри `env_mail_t`
(`src/config/appconfig.h:50`).

Требования к разбору:

* `security: "none"` без `user` — валидно (внутренний релей без аутентификации).
* `user` без `password` — ошибка конфигурации, а не молчаливая отправка без AUTH.
* `security: "none"` вместе с `user` — предупреждение в журнал: учётные данные
  уйдут открытым текстом.
* Пароль не должен попадать ни в один `log_*`, включая отладочные пути.

Про секреты в файле конфигурации: для сайта это решено — `config.json`
собирается из шаблона в entrypoint, значения приезжают из `.env` (см.
`backend/readme.md` в репозитории сайта), так что пароль в репозитории не лежит.
Отдельного механизма секретов ради этого вводить не нужно.

## 4. S.2 — Подключение к заданному хосту

`__mail_connect()` разделяется на выбор эндпоинта и собственно установку
соединения:

* **прямой режим** — как сейчас: `__mail_get_mx_servers()`, перебор записей по
  приоритету, порт 25;
* **релейный режим** — резолв `relay.host` и подключение к `relay.port`; MX не
  спрашивается вовсе, `mail_is_real()` в `send_mail()` пропускается.

Резолв релея делать через `getaddrinfo()`, а не через `__mail_get_mx_servers()`:
имя релея — это A/AAAA, и заодно снимается ограничение IPv4 хотя бы для этого
режима. Перебирать все адреса из ответа до первого успешного `connect`.

Порт перестаёт быть константой в `__mail_connection_create()` и передаётся
параметром.

Полезный побочный эффект: релейный режим не делает DNS-запросов типа MX и не
зависит от `libidn2` — путь короче и предсказуемее.

## 5. S.3 — Разбор расширений EHLO

Ответ на EHLO многострочный:

```
250-smtp.mail.ru Hello
250-SIZE 73400320
250-STARTTLS
250-AUTH PLAIN LOGIN
250 HELP
```

Сейчас из этого сохраняется только код последней строки. Нужен накопитель
возможностей в `smtpresponse_t`: флаги `STARTTLS`, `SIZE` (со значением) и
список механизмов AUTH. Достаточно фиксированного набора флагов плюс битовой
маски механизмов — произвольные расширения хранить незачем.

Это же закрывает дыру в текущем коде: `__mail_start_tls()` (`mail.c:441`)
посылает `STARTTLS` не проверив, что сервер его объявил, и решение принимает по
коду ответа. С разобранными возможностями проверка становится явной.

После успешного STARTTLS EHLO посылается повторно (это уже делается,
`mail.c:450`) — и список возможностей нужно **перечитать**: до TLS сервер, как
правило, не объявляет AUTH вовсе.

## 6. S.4 — AUTH PLAIN и AUTH LOGIN

Двух механизмов достаточно: их поддерживают все распространённые релеи, включая
`smtp.mail.ru`, `smtp.yandex.ru` и `smtp.gmail.com` (последний — с паролем
приложения). CRAM-MD5 устарел, XOAUTH2 — отдельная задача с обновлением токенов,
в этот план не входит.

**PLAIN** — одна команда, аргумент `base64("\0user\0password")`:

```
AUTH PLAIN AGluZm9AZXhhbXBsZS5jb20AcGFzc3dvcmQ=
235 Authentication succeeded
```

**LOGIN** — три шага, логин и пароль по одному в base64:

```
AUTH LOGIN            -> 334 VXNlcm5hbWU6
<base64(user)>        -> 334 UGFzc3dvcmQ6
<base64(password)>    -> 235 Authentication succeeded
```

Кодирование уже есть — `base64_encode()` / `base64_decode()` в `misc/base64.h`,
тот же модуль, которым кодируются тема письма и тело.

При `auth: "auto"` выбирать PLAIN, если сервер его объявил, иначе LOGIN, иначе —
ошибка с внятным сообщением о том, какие механизмы предложил сервер.

Требования:

* AUTH выполняется **после** TLS. Отправка учётных данных по открытому каналу
  допускается только при явном `security: "none"` и с предупреждением при
  загрузке конфигурации.
* Буферы с паролем затирать после использования (`explicit_bzero`) — в
  `user.c` примера приложения этот приём уже применяется к `salt`/`hash`.
* Код `535` (неверные учётные данные) логировать отчётливо: это самая частая
  ошибка настройки, и «Failed to send mail» о ней ничего не говорит.

## 7. S.5 — Implicit TLS (порт 465)

При `security: "tls"` TLS-рукопожатие выполняется **сразу после `connect`**, до
чтения баннера; STARTTLS не посылается.

Механика уже написана: `__mail_init_tls()` (`mail.c:955`) создаёт `SSL_CTX`,
`__mail_alloc_ssl()` и `__mail_handshake()` делают рукопожатие. Нужно лишь
вызвать это раньше в последовательности и не слать STARTTLS.

Заодно стоит закрыть то, чего нет ни в одном режиме: **проверка сертификата
релея**. Сейчас `SSL_CTX_new(TLS_method())` создаётся без хранилища доверенных
корней и без сверки имени хоста, то есть TLS защищает от пассивного
прослушивания, но не от подмены. Для канала, по которому уходит пароль, это
существенно: `SSL_CTX_set_default_verify_paths()`, `SSL_set1_host()` и
`SSL_CTX_set_verify(SSL_VERIFY_PEER)`. Выключатель (`"verify": false`) уместен
ради самоподписанных внутренних релеев.

## 8. S.6 — DKIM-подпись должна стать необязательной

**Это дефект текущей реализации, а не часть релейного режима.**

`__mail_build_content()` (`mail.c:1038`) всегда создаёт подпись:
`dkim_create_sign()` (`mail.c:1063`), и при пустом или нечитаемом ключе она
возвращает `NULL` — письмо не отправляется вообще. При этом `config.md` про
секцию `mail` утверждает обратное: «отсутствие секции равносильно пустым
значениям — письма уходят без подписи». Документация описывает поведение,
которого нет.

Это выяснилось на сайте: конфигурация без DKIM давала `DKIM error loading rsa
key` и `Failed to send mail`, и пришлось делать секцию `mail` условной в
entrypoint — генерировать её только при наличии ключа.

Для релея это тем более важно: релей обычно подписывает письма **сам**, своим
ключом и своим доменом, и вторая подпись отправителя не нужна.

Нужно: если `dkim_private` пуст или файл недоступен — собирать письмо без
заголовка `DKIM-Signature` и продолжать отправку. Отсутствие ключа при
непустом `dkim_selector` (или наоборот) — по-прежнему ошибка конфигурации:
это опечатка, а не осознанный отказ от подписи.

## 9. S.7 — Временные и постоянные ошибки

`send_mail()` возвращает `0` на любую неудачу, и вызывающий код не может
отличить «ящик не существует» (5xx, повторять бессмысленно) от «попробуйте
позже» (4xx, стоит повторить).

Минимально полезное: сохранять последний код и текст ответа так же, как это
сделано для моделей — `model_last_status()` / `model_last_error()`
(`framework/model/model.h`), то есть thread-local статус рядом с неизменной
сигнатурой. Тогда обработчик сможет ответить пользователю по-разному, а
`send_mail_async()` — решать, ставить ли задачу в очередь повторно.

Сами повторы в этот план не входят: для них нужна очередь с состоянием, а
`send_mail_async()` сейчас просто отдаёт задачу в task manager.

## 10. D.1 — Документация и мёртвая строка

`__mail_init_tls()` содержит `instance->connection->port = 587;`
(`mail.c:964`) — присваивание в структуру **после** того, как соединение
установлено на 25. На текущий сокет оно не влияет; ниоткуда больше это поле в
момент отправки не читается. Строка вводит в заблуждение и из неё выросла
неверная фраза в `frontend/docs/mail.md`:

> «Исходное соединение устанавливается на порт 25, затем выполняется команда
> `STARTTLS`, после чего клиент переключается на порт 587 и повторяет `EHLO`
> поверх TLS.»

Переключения портов не происходит и происходить не должно: STARTTLS поднимает
TLS **на том же соединении**. Строку убрать, описание исправить.

С появлением релея дополняются `frontend/docs/mail.md` (режимы доставки, AUTH,
выбор порта) и `frontend/docs/config.md` (поля `mail.relay`).

## 11. Порядок работ

S.6 первым и отдельно: он чинит существующее поведение и не зависит от
остального. Дальше S.1 → S.2 → S.3 → S.4 одной цепочкой — раньше S.4 проверить

## 12. Как проверять

Локальный приёмник (Mailpit или MailHog) в docker-compose: поддерживает
STARTTLS, implicit TLS и AUTH, показывает принятое письмо через web-интерфейс.
Проверка на живом `smtp.mail.ru` нужна отдельно — на нём проявляются вещи,
которых у локального приёмника нет: реальные лимиты, требование совпадения
`MAIL FROM` с логином, собственная подпись релея.

Сценарии:

1. `security: starttls` + `auth: plain` — письмо принято, заголовки на месте.
2. `security: starttls` + `auth: login` — то же самое.
3. `security: tls` (465) — рукопожатие до баннера, STARTTLS не посылается.
4. `security: none` без `user` — работает, в журнале нет учётных данных.
5. Неверный пароль — `535` виден в журнале отдельным сообщением.
6. Релей недоступен — ошибка за таймаут, без зависания обработчика.
7. Конфигурация **без** `relay` — прямая доставка ведёт себя ровно как до
   изменений (регрессия основного режима).
8. Конфигурация без DKIM-ключа — письмо уходит без подписи (S.6).
9. `send_mail_async()` в релейном режиме не блокирует ответ.

### Отклонения и добавления к плану

* **Отчёт об ошибке — не thread-local.** §9 предлагал `mail_last_status()` /
  `mail_last_error()` по образцу `model_last_*`. Сделано было так, потом
  переделано по замечанию: состояние живёт полями `last_status`/`last_error` на
  `mail_t` (сессия — единственный, кто знает причину) и копируется наружу через
  `send_mail_result(payload, &result)`; `send_mail()` — это тот же вызов с
  `result == NULL`. Скрытого состояния нет, ответ живёт у вызывающего, оговорка
  «действительно до следующего вызова» исчезла, а низкоуровневый API
  (`mail->start_tls`, `mail->auth`) впервые может сказать, почему вернул 0.
  Причину записывает каждый шаг, отвергающий ответ, а не только финальный сбор.
* **Порядок выбора причины.** Правило «предпочитать ответ сервера» из §9 неверно
  в одну сторону: при отказе на этапе STARTTLS/AUTH последним ответом остаётся
  `250` от EHLO, и вызывающий получил бы «успех» вместо причины. Порядок:
  явно записанная шагом причина → ответ сервера → название шага.
* **`send_mail_async()` о причине не сообщает** и сообщать не может: задача
  выполняется на потоке менеджера задач, когда обработчик уже ответил. С
  thread-local это выглядело работающим, но не работало; теперь отмечено в
  документации. Полноценный отчёт для async — коллбэк, отдельная задача.
* **`__mail_handshake` не проверял завершённость рукопожатия.** `connection->write`
  возвращает успех и на `WANT_READ`/`WANT_WRITE`, а на блокирующем сокете это
  означает исчерпанный таймаут. Без `SSL_is_init_finished()` сессия шла дальше
  писать SMTP-команды в сокет, который так и не стал TLS.
* **`EHLO` не проверял код ответа** — отказ обнаруживался только на следующей
  команде. Теперь не-250 — ошибка с текстом сервера.
* **Утечка на каждое письмо.** `__mail_connection_free()` не освобождал
  `connection_client_ctx_t`, выделенный в `connection_c_create()`. Найдено при
  перестройке жизненного цикла соединения; исправлено (request/response
  отцепляются, их владелец — `mail_t`).
* **Пустой `mail.host`.** В релейном режиме домен отправителя часто не задан
  вовсе, а `EHLO ` без аргумента и `<...@>` — синтаксические ошибки. Добавлен
  запасной вариант.
* **Socket на попытку.** В прямом режиме перебор MX переиспользовал один и тот
  же дескриптор после неудачного `connect`. Теперь каждая попытка получает свой.

### Тесты

`core/tests/unit`, +139 проверок, весь набор (101229) зелёный, в том числе под
ASan/LSan:

* `test_smtpresponse.c` — разбор строк EHLO: полный ответ, ключевое слово на
  последней строке, регистр и форма `AUTH=`, границы слов, `SIZE` без значения,
  сброс, не-250 ответы, битые строки;
* `test_smtpresponseparser.c` — тот же разбор через настоящий парсер, включая
  ответ, приходящий несколькими `read()`;
* `test_mail.c` — сборка письма без DKIM-ключа и без селектора, `Message-Id`
  без `mail.host`, `send_mail_result()` (заполнение структуры, независимость
  двух подряд идущих отправок, `NULL`-аргументы, `mail_set_error()`), и диалог AUTH
  целиком через `socketpair`: PLAIN, LOGIN, 535, механизм не предложен, AUTH не
  предложен вовсе, отказ слать пароль открытым текстом, пропуск AUTH без
  учётных данных и в прямом режиме, гейт STARTTLS, отказ на EHLO.

Для диалога через `socketpair` понадобился `SOCK_SEQPACKET`, а не `SOCK_STREAM`:
клиент читает по одному ответу на `recv()`, и заранее выложенные ответы в потоке
склеиваются в одно чтение — парсер завершает на первом, остаток буфера теряется.

### Проверка на живом сервере

Стенд (`smtpd.py` — SMTP с STARTTLS/implicit TLS/AUTH, `dnsd.py` — MX-ответчик,
драйверы на C поверх `libcwfr_framework.so`) прошёл сценарии §12:

1. `starttls` + `auth: plain` — принято, заголовки на месте, `DKIM-Signature`
   отсутствует (ключ не задан) — это же и сценарий 8;
2. `starttls` + `auth: login` — принято, логин и пароль ушли в base64;
3. `security: tls` — рукопожатие до баннера, `STARTTLS` не посылался;
4. `security: none` без `user` — работает, ни одной команды `AUTH`;
5. неверный пароль — `RESULT=0 STATUS=535 ERROR=535 5.7.8 Error: authentication failed`
   (все восемь сценариев перепроверены после перехода на `send_mail_result()` —
   результат тот же);
6. релей недоступен — ошибка сразу, без зависания;
7. прямая доставка — MX-резолв через локальный DNS, `gethostbyname`, `connect`,
   баннер получен (порт 25 на этом хосте не забиндить без привилегий, поэтому
   проверялся `__mail_connect_mx` с параметром порта, а не `send_mail` целиком);
9. `send_mail_async()` не менялся и остаётся асинхронным.

Дополнительно: самоподписанный сертификат отвергается при `verify: true` и
принимается при `verify: false`; все 12 ошибочных конфигураций `mail.relay`
останавливают запуск с внятным сообщением; `security: "none"` вместе с `user`
пишет предупреждение в журнал.

**Не проверено вживую:** отправка через настоящий `smtp.mail.ru` — на нём
проявляются лимиты, требование совпадения `MAIL FROM` с логином и собственная
подпись релея. Это остаётся за развёртыванием.
