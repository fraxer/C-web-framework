# 07 — Поэтапный roadmap и план тестирования

План разбит на фазы с критериями приёмки. Каждая фаза — сливаемая независимо,
давая ценность (фаза 0 — даже без h2).

> Перед стартом — подтвердить главное решение: **писать своё vs `nghttp2`**
> (`00-overview.md` §2). Ниже предполагается **своя реализация**.

---

## Фаза 0 — Предпосылки (≈1–1.5 нед.)

**Цель:** починить SSL I/O, завести ALPN-скаффолд и `timerfd`, не сломав h1.1.

Задачи:
1. ✅ **ГОТОВО.** `openssl_io_status()` + перевод `__read`/`__wr` на `SSL_get_error`
   (`04` §1). Заодно добавлен `SSL_ERROR_WANT_WRITE` в `__handshake`.
2. ✅ **ГОТОВО.** ALPN-select callback на SSL_CTX (приоритет h2 > http/1.1);
   ветвление h2/h1.1 в `__handshake`; заглушка `set_http2` шлёт SETTINGS +
   GOAWAY(NO_ERROR) (`04` §2).
3. ✅ **ГОТОВО (фаза 5).** `timerfd` на воркер + тегирование событий
   (`ev.data.ptr = &timer_tag`) — диспетчер отличает тик таймера от события
   соединения и зовёт `api->on_tick` (sweep idle/PING/shutdown). Раньше было
   отложено, т.к. `__mpx_epoll_process_events` жёстко трактовал `ev->data.ptr`
   как `connection_t*`, а потребителей не было до фазы 5.
4. ✅ **ГОТОВО (отдельным follow-up'ом, 2026-08-02).** `SSL_CTX_set_ciphersuites`
   для TLS 1.3. Одно поле `ciphers` разбирается `openssl_split_ciphers()` на две
   группы (1.3 — токены с префиксом `TLS_`), каждая уходит своему API;
   разделителями считаются `:`, `,` и пробел (как в `ciphers(1)`). Пустая группа
   = дефолты OpenSSL для этой версии, а не пустой список. До этого 1.3-имена в
   конфиге молча игнорировались, хотя формат был описан в документации.

**Критерии приёмки (проверено вживую):**
- ✅ `openssl s_client -alpn h2` → `ALPN protocol: h2`; `http/1.1` → `http/1.1`;
  оба → `h2` (приоритет сервера).
- ✅ Сервер шлёт GOAWAY(NO_ERROR) — перехвачено ровно 26 байт (SETTINGS 9B +
  GOAWAY 17B), декодировано корректно. TLS-хендшейк не сломан.
- ✅ `curl --http1.1 -k https://…/` → HTTP 200; 56794/56794 unit-тестов зелёные.
- ✅ WANT_READ/WANT_WRITE обрабатываются через `openssl_io_status`; h1.1-over-TLS
  отрабатывает на 200 без ложных разрывов. Debug-сборка с ASan чиста.
- ✅ TLS 1.3 ciphers (п. 4), проверено `openssl s_client`: конфиг
  `TLS_AES_128_GCM_SHA256:ECDHE-RSA-AES128-GCM-SHA256` → 1.3 согласует ровно
  `TLS_AES_128_GCM_SHA256`, а клиент, требующий `TLS_CHACHA20_POLY1305_SHA256`
  или `TLS_AES_256_GCM_SHA384`, получает handshake failure (до фикса сервер
  принимал все три — 1.3-список был дефолтным). Конфиг только с 1.2-именами →
  1.3 продолжает работать на дефолтах; только с 1.3-именами → 1.2 работает на
  дефолтах. Несуществующая suite (`TLS_NO_SUCH_SUITE`) → сервер не стартует с
  `Openssl error: TLS 1.3 ciphersuites are invalid`. ALPN, h2, h1.1 и h2spec
  (147 тестов, 0 failed) не затронуты; 8 unit-тестов на токенайзер.

> **Затронутые файлы** (подмодуль `backend/core`, НЕ закоммичены):
> `src/openssl/openssl.{h,c}`, `protocols/http/server/httpserverhandlers.c`,
> `protocols/http/server/filters/http_write_filter.c`.

> ⚠️ **Поведение во время фаз 0–2** (снято фазой 3): ALPN всегда рекламирует
> h2, и до фазы 3 заглушка отвечала GOAWAY. Начиная с фазы 3 h2 обслуживается
> по-настоящему, поэтому гейт `http2.enabled` («Решения» №7) больше не нужен
> для шипабельности ветки.

## Фаза 3 — Один поток h2-over-TLS (≈2 нед.)

**Цель:** сквозной цикл для одного потока — доказать интеграцию с `httpctx_t`.

Задачи по `05`: сборка `httprequest_t` из HEADERS/DATA, `h2_write_filter`,
сопряжение с `httprequest_t`/`httpresponse_t`. Мультиплексирование пока не
требуется — одновременно один активный поток (как proof-of-concept).

**Критерии приёмки (проверено вживую, curl 8.18 + собственные raw-пробы):**
- ✅ `curl --http2 https://<vhost>/` отдаёт страницу: статика, `send_data`,
  `send_json`, 404, HEAD, keep-alive (3 запроса на одном соединении).
- ✅ Файл 2.8 МБ отдаётся байт-в-байт (много DATA-фреймов + flow control).
- ✅ POST принимается: JSON (500 КБ — с WINDOW_UPDATE на приёме), urlencoded.
- ✅ Range/multipart-byteranges (206), gzip, cookies — работают как в h1.1.
- ✅ Регрессия h1.1 на том же порту (ALPN `http/1.1`) не затронута.
- ✅ Send-side flow control: при `SETTINGS_INITIAL_WINDOW_SIZE=100` сервер
  отдаёт ровно 100 байт и встаёт; после `WINDOW_UPDATE` докачивает до конца.
- ✅ Негативные пути дают GOAWAY(PROTOCOL_ERROR), не падение: битый preface,
  битый HPACK-блок, HEADERS на stream 0, oversize length, PUSH_PROMISE от
  клиента, `WINDOW_UPDATE` с inc=0. PING → PING+ACK.
- ✅ **`h2spec` 2.6.0 — 146/146 зелёных**, в strict-режиме (`-S`) 147/147.
  Прогнан и на Release-, и на Debug-сборке (ASan/LSan чисты, находок нет).
- ✅ Debug-сборка (ASan+LSan+`-fanalyzer`) чиста под нагрузкой;
  57694/57694 unit-тестов зелёные.

**Реализовано:**
- `protocols/http2/server/h2session.{h,c}` — сессия на соединение: read/write
  guards, диспетчеризация фреймов, сборка `httprequest_t` из HEADERS/DATA
  (spool тела в tmp-файл, как h1.1), SETTINGS/PING/WINDOW_UPDATE/RST_STREAM/
  GOAWAY, окна приёма и передачи, буфер исходящих фреймов.
- `protocols/http2/server/h2_write_filter.{h,c}` — терминальная стадия
  фильтр-цепочки: HEADERS (HPACK + CONTINUATION при переполнении
  max_frame_size) и DATA-фреймы прямо из буфера вышестоящего фильтра.
- `filters_create_h2()` (`http_filter.c`) — цепочка not_modified → range →
  data → gzip → **h2_write** (без chunked). `httpresponse_create_h2()` и флаг
  `connection_server_ctx_t.is_http2` выбирают её.
- Переиспользовано без изменений: роутинг, middleware, очередь хендлеров,
  фильтры range/gzip/not_modified/data, ORM, `send_*` — ABI хендлеров не
  тронут.
- Вынесены для переиспользования: `http_server_dispatch`,
  `__run_header_filters`/`__run_body_filters`, `httpparser_select_server`
  (выбор виртуального хоста по `:authority`), `httprequest_create_payload_file`,
  `h2frame_encode_header`, `hpack_encoder_set_max_table_size` (корректный
  dynamic table size update вместо молчаливого resize).
- Приведено к RFC по итогам h2spec (26 падавших тестов → 0):
  - **машина состояний потока** (§5.1: idle/open/half-closed/closed) — DATA,
    RST_STREAM и WINDOW_UPDATE в неверном состоянии теперь дают
    PROTOCOL_ERROR/STREAM_CLOSED вместо молчаливого игнора;
  - **разделение ошибок на stream и connection** (§5.4): некорректный запрос
    гасит только поток (RST_STREAM), а не соединение;
  - **валидация запроса** (§8.2/§8.3): обязательный и единственный `:scheme`,
    запрет неизвестных и ответных псевдо-заголовков, псевдо-заголовки строго до
    обычных, `TE` только со значением `trailers`, сверка `content-length` с
    суммой DATA;
  - **трейлеры** — HEADERS после DATA принимаются (поля отбрасываются),
    псевдо-заголовки в них и второй блок без END_STREAM → PROTOCOL_ERROR;
  - `SETTINGS_ENABLE_PUSH` вне {0,1} и переполнение окна WINDOW_UPDATE
    (FLOW_CONTROL_ERROR на соединении и на потоке);
  - самозависимый PRIORITY (§5.3.1) → stream error;
  - HPACK: dynamic table size update разрешён только в начале блока (§4.2);
  - reserved R-бит фрейма игнорируется (§4.1), а не отвергается.
  Отвергнутый или сброшенный поток всё равно прогоняет свой HPACK-блок через
  декодер — общая на соединение динамическая таблица иначе рассинхронизируется.

**Известные ограничения (закрываются фазой 4):**
- Один активный поток на соединение; сервер честно анонсирует
  `SETTINGS_MAX_CONCURRENT_STREAMS=1`, лишние потоки получают RST_STREAM
  (REFUSED_STREAM). curl при этом открывает дополнительные соединения.
- Flow control учитывается на уровне соединения и текущего потока; полноценных
  окон на N потоков и outbox-сериалайзера ещё нет.
- Trailers, PRIORITY (игнорируется), h2c, PUSH — вне фазы.

## Фаза 4 — Мультиплексирование + flow control (≈2–2.5 нед.)

**Цель:** N параллельных потоков, flow control, WINDOW_UPDATE.

Задачи по `03` §3–§4, `06` §2: stream table, окна send/recv на поток,
сериализация записи, обработка SETTINGS.

### Сделано (первый заход)

- `protocols/http2/server/h2stream.{h,c}` — `h2stream_t` и таблица потоков на
  сессии. Односвязный список: `MAX_CONCURRENT_STREAMS` держит его в пределах
  сотни, и линейный поиск дешевле хеша с аллокацией ключей.
- **Запрос и ответ переехали на поток.** `connection_server_ctx_t.request/
  response` — один на соединение, для N потоков этого не хватает. Теперь на
  h2-соединении они остаются NULL, а `httprequest_t`/`httpresponse_t` живут в
  `h2stream_t`. Швы: `h2_server_attach_response` (привязка ответа при создании
  в `__handle`), `__handler_finished` (общая точка возврата хендлера) и
  `h2_server_response_ready` (пометить поток готовым и разбудить запись).
- **Окна flow control на каждый поток** плюс connection-level; DATA режется по
  `min(max_frame_size, окно потока, окно соединения)`. `SETTINGS_INITIAL_
  WINDOW_SIZE` применяется дельтой ко всем открытым потокам (§6.9.2).
- **Сериализация записи.** Поток, остановившийся посреди фрейма, удерживает
  сокет (`session->writing`), иначе его байты вклинились бы в чужой DATA-фрейм.
  Поток, упершийся в окно, останавливается на границе фрейма — сокет свободно
  переходит к следующему готовому потоку.
- **Дренаж очереди хендлеров** больше не завязан на запись: цепочку
  `connection_after_write` h2-путь вести не может (он выходит раньше при
  насыщенном сокете или пустом окне), поэтому её ведёт
  `h2_server_response_ready`.
- `MAX_CONCURRENT_STREAMS` поднят с 1 до 100; сверх лимита — RST_STREAM
  (REFUSED_STREAM).

**Проверено:**
- ✅ 100 потоков на одном соединении — все обслужены; 130 → ровно 30
  REFUSED_STREAM, остальные 100 в порядке.
- ✅ 30 × 2.8 МБ на одном соединении: каждый поток получил ровно 2 880 040
  байт (86 МБ за 0.2 с). Смешанная нагрузка 100 потоков (4 типа ответов) —
  размеры точные для каждого.
- ✅ Ответы **чередуются**: порядок завершения не совпадает с порядком запросов.
- ✅ `curl --parallel` (10 запросов) теперь использует **одно** соединение
  вместо трёх.
- ✅ RST_STREAM посреди отдачи ответа: соединение выживает, ASan чист.
- ✅ `h2spec -S` 147/147; unit-тесты 57694/57694; Debug (ASan/LSan/`-fanalyzer`)
  чист под нагрузкой; h1.1 на том же порту не затронут.

### Вынесено из фазы 4 в отдельный план

**Конкурентное исполнение хендлеров на одном соединении** →
`docs/concurrency/00-handler-concurrency.md`.

Ограничение живёт не в h2-слое: `connection_queue_guard_pop` отдаёт соединение
с уже взятым `connection_s_lock` и держит его весь вызов хендлера, поэтому
хендлеры одного соединения сериализованы одинаково для h1.1, h2 и WebSocket
(у разных соединений — параллельны). Именно это свойство позволило всем
h2-структурам обойтись без собственных блокировок, так что трогать его нужно
осознанно и отдельно. Аудит показал, что область изменения узкая (состояние
одного соединения), а не «вся модель блокировок» — подробности, гонки и фазы
в отдельном документе.

### Нагрузка `h2load` (инструмент установлен позже)

Стенд: loopback + TLS, `workers=4 threads=8`, Release. Заявленный критерий
приёмки — первая строка.

| Сценарий | req/s | Результат |
|---|---|---|
| `-n 10000 -c 100 -m 100` (критерий приёмки) | 99 352 | 10000/10000, 0 failed |
| `/json`, 100 conn × 100 streams | 154 780 | 20000/20000 |
| `/json`, 100 conn × 1 stream | 76 743 | 20000/20000 |
| `/json`, HTTP/1.1, 100 conn | 82 543 | 20000/20000 |
| статика `/`, 100 × 100 | 130 687 | 20000/20000 |
| gzip `page.html`, 50 × 50 | 97 875 | 10000/10000 |
| 2.8 МБ × 400, 20 × 20 | 925 (2.5 ГБ/с) | 400/400 |
| POST 500 КБ, 20 × 20 | 1 345 | 1000/1000 |
| `-m 200` (вдвое выше нашего лимита) | 128 816 | 4000/4000 |

Выводы:
- **Мультиплексирование даёт 2×**: 154 780 (m=100) против 76 743 (m=1) на том
  же числе соединений. Это и есть измеренная ценность фазы 4.
- **h2 обгоняет h1.1 на 87%** при равном числе соединений (154 780 против
  82 543) — за счёт мультиплексирования. Прогноз из «Сохранённых метрик»
  подтвердился.
- ⚠️ **Число воркеров решает всё.** При `workers=1 threads=2` h2 показывал
  44 720 против 56 918 у h1.1, то есть *проигрывал* 21%, и m=100 не отличался
  от m=1 (44 720 / 44 331): единственный воркер был насыщен, и мультиплексировать
  было нечем. Сравнивать h2 с h1.1 на одном воркере бессмысленно.
- `-m 200` при анонсированном лимите 100: h2load ставит лишние потоки в
  очередь, все 4000 обслужены — `SETTINGS_MAX_CONCURRENT_STREAMS` уважается.
- **Память не растёт**: RSS 81 996 → 82 088 КБ после 250 000+ потоков на
  одиночных долгоживущих соединениях (прирост — буферы deflate, выходит на
  полку). Утечки таблицы потоков нет.

Под Debug (ASan + LSan + `-fanalyzer`) тот же набор: все запросы успешны,
находок нет, `LeakSanitizer: checking for leaks` отрабатывает при выходе и
ничего не сообщает; h2spec 147/147.

### Авто-масштабирование recv-окна (хвост фазы 4) ✅

Механика — в `03` §4, «Авто-масштабирование recv-окна». Здесь — почему и с
какими числами.

**Мерили до того, как делать.** `tc netem` требует root, поэтому длинный толстый
канал эмулировался userspace-прокси с линией задержки (читающая и пишущая задачи
через очередь `(deadline, chunk)`; наивный вариант «прочитал → поспал → записал»
сам режет полосу до `chunk/delay` и маскирует ровно то, что мы измеряем).
Клиент — `h2load -n1 -c1 -m1 -d body8m.bin`, тело 8 МБ, хендлер тело
игнорирует. Порядок: замер потолка → фиксированное большое окно → авто-скейлер.

| RTT | окно 64 КБ | окно 4 МБ (фикс.) | авто (64 КБ → 4 МБ) |
|---|---|---|---|
| 0 (loopback) | 19 мс | — | 21 мс |
| 50 мс | 7.57 с | 0.21 с | 0.69 с |
| 100 мс | 14.95 с | 0.41 с | 1.34 с |

- Потолок совпал с теорией `окно / RTT` с точностью до процентов: 1.06 МБ/с при
  RTT 50 мс (теория 1.31) и 0.53 МБ/с при RTT 100 мс (теория 0.64).
- **Потоки не помогают.** 8 потоков × 1 МБ на RTT 50 мс: 10.23 с против 9.17 с
  у одного потока на 8 МБ — упирается окно **соединения**, мультиплексирование
  здесь ни при чём. После изменения — 0.85 с.
- Авто-скейлер отстаёт от заранее выставленного 4 МБ (0.69 против 0.21 с) —
  это цена рампы: удвоение раз в круг, 64 КБ → 4 МБ за 6 кругов. Кто знает своих
  клиентов, поднимает `http2_recv_window_initial` и платит только первым RTT.
- На loopback окно не растёт (21 мс против 19 мс до изменения): измеренный BDP
  не дотягивает до 65535. Регресса на быстрых каналах нет.

⚠️ Грабли стенда: прокси в userspace ломает `TCP_INFO` — ядро видит loopback-RTT
до прокси, а не 100 мс до клиента, и первый прогон авто-скейлера не дал ничего.
Это не артефакт стенда, а настоящий кейс «TCP-балансир перед сервером»; чинится
tune-PING'ом, который и был из-за этого добавлен.

**Проверено:** h2spec 145/146 (1 skip, 0 failed) — ровно как на коде до
изменений, скип в 6.9.2 предсуществующий; тот же результат под Debug
(ASan/LSan/`-fanalyzer`); загрузки 8 МБ ×1, 8 × 1 МБ, 200 × 1 МБ на 4
соединениях под ASan — все успешны, находок нет.

### Планирование записи между готовыми потоками ✅

Последний хвост фазы 4. Формулировка «приоритизация — сейчас порядок таблицы»
оказалась неточной: порядок был вторичен, а мешало то, что запись шла **до
конца ответа**.

`h2_write()` обходил таблицу и для каждого готового потока гнал фильтр-цепочку
целиком. При насыщении сокета поток пиннился в `s->writing`, и дальше каждый
EPOLLOUT обслуживал только его — до последнего байта. Большой файл занимал
соединение целиком; мелкие запросы ждали не «своей очереди», а конца загрузки.
Это ровно та head-of-line блокировка, ради устранения которой мультиплексируют.

Приоритетов RFC здесь нет и не будет: дерево зависимостей из RFC 7540 объявлено
deprecated в RFC 9113 §5.3, так что политика планировщика — целиком наша.

Сделано три вещи:

1. **Квант записи.** `h2stream_t.write_credit` пополняется на входе в
   `h2_write_stream()` из `http2_write_quantum` (по умолчанию 64 КБ = 4 кадра
   при дефолтном max frame size) и тратится в DATA-цикле write-фильтра. Когда
   кредит исчерпан, фильтр останавливается **на границе кадра**, поднимает
   `stream->yielded` и возвращает `CWF_EVENT_AGAIN` — тот же путь возобновления,
   что и при EAGAIN сокета.
2. **Снятие лишнего пина.** `H2_WRITE_WINDOW` и новый `H2_WRITE_YIELD` больше не
   пиннят поток в `s->writing`: оба означают остановку на границе кадра, где
   сокет свободен. Пин остаётся только для `H2_WRITE_SOCKET` — там кадр может
   быть записан наполовину. Раньше поток, упёршийся в **своё** окно, держал всё
   соединение до WINDOW_UPDATE.
3. **Round-robin.** Таблица получила `streams_tail`, вставка стала в хвост
   (было — в голову, то есть де-факто LIFO), а поток, остановившийся не доделав
   ответ, уезжает в хвост через `h2stream_rotate()`. Позиция в списке и есть
   курсор round-robin. Бит `served` не даёт обойти один поток дважды за проход:
   ротация подкладывает потоки позади курсора.

**Где нельзя yield'иться.** Только в body-фазе и только на границе кадра.
Посреди кадра — вклинятся чужие байты. В header-фазе — второй поток закодирует
свой блок, пока блок первого ещё не отправлен, и у пира разъедется HPACK-декодер
(блоки обязаны приходить в порядке кодирования, §4.3). Инвариант «незаписанный
закодированный блок есть максимум у одного потока, и он владеет сокетом»
держится сам: EAGAIN в `__header` даёт `H2_WRITE_SOCKET`, то есть пин.

#### Замеры

Стенд: Debug-сборка (ASan/LSan), TLS, loopback, файл 256 МБ + два мелких ответа
на одном соединении, окна подняты (`-w30 -W30`), чтобы мерить планировщик, а не
flow control. Метрика — `responseEnd` мелкого `/asset.txt`, 16 прогонов.
«До» эмулировано через `http2_write_quantum = 1 ГБ`.

| | медиана | p90 | max | прогонов с блокировкой >50 мс |
|---|---|---|---|---|
| до (до конца ответа) | 207 мс | 222 мс | 232 мс | 10/16 |
| после (квант 64 КБ) | 0.90 мс | 1.00 мс | 2 мс | 0/16 |

Пропускная у самой загрузки не пострадала: 256 МБ в одиночку — 208–232 мс до и
после, лишний оборот epoll на каждые 64 КБ теряется в шуме.

⚠️ На 3 МБ эффекта не видно — файл целиком уходит в буфер сокета, и разброс
съедает разницу. Нужен файл, который гарантированно насыщает сокет:
`head -c 268435456 /dev/urandom > test_root/huge.bin`.

**Проверено:** h2spec 147 тестов, 146 passed, 1 skipped (предсуществующий 6.9.2),

## Фаза 5 — Жизненный цикл ✅

**Цель:** idle-timeout, PING-watchdog, GOAWAY-дренаж, корректный teardown по
SIGTERM, и перенос `timerfd`-инфраструктуры из фазы 0.

### Сделано

- **`timerfd` на воркер + тегирование событий** (отложенное из фазы 0). Один
  `timerfd` (CLOCK_MONOTONIC, тик ≈500 мс) регистрируется в epoll воркера с
  `ev.data.ptr = &api->timer_tag` — уникальным адресом-маркером.
  `__mpx_epoll_process_events` отличает событие таймера от события соединения
  сравнением указателя, дренирует level-triggered fd (8-байтный счётчик) и зовёт
  `api->on_tick`. Неудача создания таймера не фатальна — воркер просто работает
  без sweep'а.
- **Список соединений воркера.** `connection_t` получил intrusive-поля
  `prev/next`; `mpxapi_t::conns` — голова списка. Поддерживается в
  `control_add`/`control_del` (только на потоке воркера — без блокировки). База
  для sweep'а.
- **Политика жизненного цикла на h2-сессии** (`h2session_t`):
  `last_activity_ms`, `ping_sent_ms`, `ping_payload[8]`, `draining`. Активность
  обновляется только на **полученных** байтах (фрейм или PING-ACK) — никогда на
  собственных записях, чтобы исходящий ответ не маскировал замолчавший клиент.
- **`h2_server_tick(connection, shutdown_now)`** — точка входа sweep'а. Владеет
  жизненным циклом блокировки: `trylock` (занятое соединение пропускается до
  следующего тика), и каждый выход освобождает её (через close или явно).
  Решает: idle-timeout, watchdog-PING, drain по shutdown. Закрытие идёт через
  новый `connection_close_locked` (без повторного захвата спинлока — sweep уже
  держит его).
- **Idle-timeout.** При `now - last_activity_ms ≥ idle_timeout` и отсутствии
  активных потоков → `GOAWAY(NO_ERROR)` + `connection_close_locked`. По умолчанию
  120 с; `stream_count==0` — соединение между запросами, а не в середине работы.
- **PING watchdog.** После `ping_interval` тишины шлётся PING с уникальным
  8-байтным opaque-payload (монотонный счётчик); ответный ACK сверяется по
  payload и гасит watchdog. ACK не пришёл за `ping_ack_timeout` → GOAWAY+close.
  По умолчанию выключен (здоровому соединению лишний трафик не нужен; idle
  уже убирает молчащих клиентов) — включается оператором для каналов, где
  серверу нечего отправить. Одновременно висит ровно один PING.
- **GOAWAY-дрейн (RFC 9113 §6.8).** После `goaway_sent` новые потоки с
  `id > last_stream_id` получают `RST_STREAM(REFUSED_STREAM)` (HPACK-блок
  предварительно декодируется — общая таблица должна оставаться в синхроне).
  Потоки ≤ границы, отправленные клиентом в flight до GOAWAY, обслуживаются.
- **SIGTERM/SIGTERM-graceful** (`apps/server/main.c`). Раньше `sigwait` →
  немедленный `exit(0)`. Теперь: `appconfig->shutdown=1`,
  `module_loader_wakeup_all_threads()` (будит handler-потоки), затем bounded-wait
  по `appconfig->threads_count` в окне `http2_shutdown_grace_sec` (по умолчанию
  5 с). Воркеры видят shutdown на ближайшем тике таймера и запускают
  GOAWAY-дрейн; активные потоки дорабатывают, затем соединение закрывается.
  Best-effort: медленный клиент не может остановить shutdown — по истечении grace
  выполняется существующий terminate.

### Настройки (`config.json` → `main.env`)

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `http2_idle_timeout_sec` | 120 | 0 = выключить idle-timeout |
| `http2_ping_interval_sec` | 0 | 0 = выключить watchdog; иначе шлёт PING после N с тишины |
| `http2_ping_ack_timeout_sec` | min(interval, 15) | grace на ответ PING |
| `http2_shutdown_grace_sec` | 5 | окно drain'а по SIGTERM |
| `http2_settings_ack_timeout_sec` | 10 | 0 = выключить проверку `SETTINGS_TIMEOUT` (§6.5.3); добавлено фазой C плана `08` |

| `http2_recv_window_max` | 4 МБ | потолок авто-масштабирования; равен `initial` → окно зафиксировано, скейлер выключен |
| `http2_write_quantum` | 65536 | сколько байт тела поток отдаёт за один круг, прежде чем уступить сокет соседям (минимум 1024) |

## Фаза 6 — h2c (≈1 нед.) — ✅ ГОТОВО

**Цель:** HTTP/2 поверх открытого текста.

Задачи по `04` §3: prior-knowledge (снифф preface в `__read`) + Upgrade
(через `switch_to_protocol`).

### Реализовано

- **Prior-knowledge (§3.4).** `__set_protocol` ставит `ctx->h2c_preface` только
  на plaintext-листенере (TLS не трогаем — там протокол уже выбран ALPN'ом).
  Первый `__read` разбирает начало потока: 24 байта preface → HTTP/2, иначе —
  обычный h1.1. Решение принимается один раз за соединение, дальше h1.1 идёт
  прежним быстрым путём.
  `h2_server_set_http2_prior_knowledge()` строит сессию и скармливает ей уже
  прочитанные байты (`h2_session_feed`), так что SETTINGS/HEADERS, приехавшие в
  том же пакете, разбираются сразу.
- **Upgrade (§3.2).** `h2c_upgrade()` (экспортируется из `h2session.h`) ловит
  `Upgrade: h2c` + `HTTP2-Settings` + `Connection: …, HTTP2-Settings`,
  декодирует base64url-payload, ставит 101 Switching Protocols и вешает
  `switch_to_protocol`. После того как 101 ушёл в сокет,
  `h2_server_set_http2_upgrade()` строит сессию, применяет настройки пира из
  заголовка и делает **stream 1** из уже разобранного HTTP/1.1-запроса —
  без повторного HPACK-декодирования. Дальше поток идёт по обычному
  `h2_dispatch`, ответ возвращается HEADERS/DATA на stream 1.
- **Подключение в приложении:** middleware `middleware_h2c_upgrade`
  (`app/middlewares/`), регистрируется в `middlewarelist.c`; включается
  добавлением в `"middlewares"` нужного plaintext-vhost'а. Контракт middleware
  инвертирован относительно `h2c_upgrade()`: 0 — цепочка остановлена (101
  отправлен, хендлер не запускается), 1 — обычный запрос.
- **Общая точка входа.** `h2_session_begin()` — единственный конструктор сессии
  для всех трёх путей (TLS ALPN, prior-knowledge, Upgrade);
  `h2_drain_and_rearm()` — общий хвост (flush + выбор EPOLLIN/EPOLLOUT).
  `h2_apply_settings_payload()` разделён между SETTINGS-фреймом и
  `HTTP2-Settings`-заголовком.
- **Владение запросом при смене протокола.** `__ctx_reset` больше не освобождает
  `ctx->request`, если висит `switch_to_protocol`: h2c-апгрейд забирает этот
  запрос под stream 1. Websocket-переключатели освобождают его сами (ровно то,
  что раньше делал reset).
- **base64url** (`misc/base64.{h,c}`) — алфавит RFC 4648 §5 без padding'а, для
  `HTTP2-Settings`.

### Найдено и исправлено по ходу

- **Клиентский preface после 101.** Сессия для Upgrade строилась с
  `preface_required = 0` — по ошибочному прочтению, будто `HTTP2-Settings`
  заменяет preface. По §3.2 клиент шлёт preface сразу по получении 101, и эти
  24 байта разбирались как фрейм → `GOAWAY(PROTOCOL_ERROR)`. `nghttp` баг не
  ловил: он закрывает соединение сразу после ответа. Теперь preface ждут все три
  входа, и параметр из `h2_session_begin()` убран.
- **Preface, разорванный между TCP-сегментами.** Снифф сравнивал только если
  `bytes_readed >= 24`; при разрыве (или побайтовой отправке) обрывок уезжал в
  h1.1-парсер → 400. Теперь байты накапливаются в начале `connection->buffer`
  (`ctx->h2c_peeked`), следующее чтение дописывается за ними, и победивший
  протокол получает весь префикс целиком.
  `MSG_PEEK` не подошёл: на level-triggered epoll непрочитанные байты заставляют
  EPOLLIN срабатывать снова и снова — клиент, замерший посреди preface, крутил бы
  воркер на 100% CPU. Проверено: замерший клиент — 0% CPU.
- **UAF на graceful shutdown (регрессия фазы 5).** `main()` опрашивал
  `cfg->threads_count`, но поток, уронивший счётчик до нуля, тут же освобождает
  сам `cfg` — ASan падал на каждом SIGTERM. Добавлен счётчик с временем жизни
  процесса (`appconfig_threads_alive()`), решение об освобождении принимается по
  значению из `fetch_sub` (иначе два потока могут увидеть ноль и освободить
  дважды).
- **`Content-Length` на 101/204.** `http_data_filter` ставил `Content-Length`
  всем статусам кроме 304; RFC 9110 §8.6 запрещает его на 1xx и 204. Касалось и
  websocket-хендшейка — теперь оба ответа без него.

### Критерии приёмки (проверено вживую)

- ✅ `curl --http2-prior-knowledge http://…/` → HTTP/2 200; `/json`, POST,
  файл 3 МБ — байт-в-байт.
- ✅ `nghttp --upgrade` и `curl --http2` (Upgrade) → HTTP/2 200; POST с телом
  через Upgrade доезжает до хендлера (тело уже разобрано h1.1-парсером).
- ✅ h1.1 на том же порту не сломан: `/`, статика, keep-alive ×3 — 200 HTTP/1.1.
- ✅ Preface по одному байту с задержками 0/2/10 мс — 15/15 сессий поднялись.
- ✅ Мультиплексирование поверх h2c: `h2load -n500 -c4 -m20` → 500/500 2xx.
- ✅ **`h2spec` по TLS: 146/146, strict 147/147** — регрессии от h2c нет.
- ✅ **`h2spec` по h2c (plaintext): 144 passed, 1 skipped, 1 failed.**
  Единственный провал — §3.5.2 «Sends invalid connection preface»: на порту,
  который обслуживает и h1.1, мусорный preface — это просто битый HTTP/1.1-запрос,

  GOAWAY, потому что считает порт чисто-h2. Поведение верное, тест неприменим к
  смешанному порту; по ALPN (порт только-h2) этот же тест зелёный.
- ✅ Unit-тесты 57694/57694; Debug (ASan+LSan+`-fanalyzer`) и Release собираются

(`PUSH_PROMISE`, `response->push()`, лимиты, `ENABLE_PUSH`), прошла приёмку —
h2spec strict 147 тестов / 0 failed, 3 МБ через пуш под flow control, отмена
пуша в середине тела, ASan/LSan чисты — и **удалена по решению владельца
проекта**. Ниже причины, чтобы через полгода не переписывать это заново.

### Почему отказались

- **Клиентов нет.** Chrome убрал server push в 106, Firefox и Safari
  отключили по умолчанию, CLI `curl` пуш не включает ничем. Все они шлют
  `SETTINGS_ENABLE_PUSH=0`, а сервер обязан это соблюдать (§8.4: отправка
  `PUSH_PROMISE` после этого — connection error). То есть на публичном вебе
  код гарантированно не исполнялся бы никогда.
- **Отрасль откатилась, а не «пока не завезла».** nginx удалил `http2_push`
  в 1.25.1 — вместе с директивами, не задепрекейтил. Cloudflare свой пуш
  выключил. Замена — `103 Early Hints` с `Link: rel=preload`, где решение
  остаётся за клиентом и не тратит окно соединения на то, что уже в кеше.
- **Цена — не строки, а инвариант.** Сам по себе пуш opt-in на уровне вызова
  и стоил бы ноль, пока его не зовут. Но он вносил в write-путь обязательный
  этап (выпуск промисов до тел ответов, в порядке возрастания id, только когда
  ни один фрейм не разорван) и счётчик вложенного диспетча `push_dispatch`,
  корректный лишь при сериализованных хендлерах одного соединения. Ровно этот
  инвариант ломает план `docs/concurrency/00-handler-concurrency.md`. Платить
  за фичу с нулём пользователей в задаче, которая и так сложная, — плохой
  размен.

### Если возвращать

Реализация лежит в истории — коммит был снят `reset`'ом до публикации, но
подход воспроизводим по этому разделу:

1. Промисы копить на потоке и выпускать **с write-пути**, по возрастанию
   обещанного id, до тел ответов. Три причины сходятся в одну точку: §5.1.1
   требует резервировать id по возрастанию; байты промиса нельзя вписывать в
   недописанный чужой DATA-фрейм; `PUSH_PROMISE` легален, только пока
   ассоциированный поток открыт.
2. Границу idle/closed для **чётных** id считать по счётчику серверных
   потоков, а не по `last_stream_id` (он про клиентские). Иначе законный
   `RST_STREAM` клиента по пуш-потоку превращается в
   `GOAWAY(PROTOCOL_ERROR)` — это стоило отладки.
3. Вложенный диспетч (пуш статики завершается синхронно внутри чужого
   хендлера) не должен будить соединение: воркер уже держит его в руках.
   Признак вложенности привязывать **к потоку исполнения**, а не к сессии.
4. Считать клиентские и серверные потоки раздельно, иначе пуши съедают слоты
   `MAX_CONCURRENT_STREAMS`, обещанные клиенту.
5. Причину отказа в пуше логировать: «хендлер ничего не запушил» иначе
   неотличимо между «клиент выключил пуш» и «упёрлись в лимит».

**Статус плана HTTP/2: фазы 0–6 закрыты, фаза 7 закрыта отказом, TLS 1.3
ciphers сделаны, оба follow-up'а фазы 4 (авто-масштабирование recv-окна и
планирование записи между готовыми потоками) закрыты.** Открытых пунктов плана
не осталось.

> Этот план был про то, чтобы h2 заработал. Аудит от 2026-08-03 показал, что
> сверх него в спецификации остаются незакрытые места — приёмная сторона flow
> control, DoS-бюджеты (Rapid Reset, CONTINUATION, MAX_HEADER_LIST_SIZE),
> валидация октетов в полях, точность кодов ошибок, Extended CONNECT, трейлеры,
> 1xx. Они собраны отдельным планом: `08-spec-gaps.md`. `h2spec` их не ловит —
> почему, там же в §1.

## План тестирования

### Unit-тесты (в `core/tests/`, `BUILD_TESTS=yes`)
- HPACK: RFC 7541 Appendix C + round-trip + фаззинг блоков.
- Фрейм-парсер: разрывы фрейма, все типы, валидации из `03` §8.
- Stream-FSM: переходы состояний, запрещённые фреймы.
- Flow control: WINDOW_UPDATE, переполнение, SETTINGS-delta.

### Спецификация-совместимость
- **`h2spec`** (https://github.com/summerwind/h2spec) — основной инструмент
  соответствия RFC 9113/7540. Запускать на каждом чекпоинте:
  `h2spec -h 127.0.0.1 -p <порт> -t -k -S`. С фазы 3 — 100% зелёный (147/147 в
  strict-режиме); держать таким на каждом слиянии.
- **RFC 9112/9113** и **RFC 7541** как первоисточник проверок.

### Нагрузка/интероперабельность
- **`h2load`** (из nghttp2) — пропускная способность, мультиплексирование.
- **`curl`** (`--http2`, `--http2-prior-knowledge`) — базовая интероперабельность.
- **`nghttp`/`nghttpd`** — второй независимый клиент/сервер для сверки.
- **браузеры** (Chrome/Firefox) — реальные сценарии, таймауты.
- **OpenSSL `s_client -alpn h2`** — проверка ALPN.
- **Wireshark** (декодер HTTP/2) — ручная сверка фреймов при отладке.

### Регрессии
- Существующие тесты HTTP/1.1, WebSocket, broadcast — обязаны оставаться зелёными
  на каждом слиянии.
- Debug-сборка с ASan + LeakSanitizer + `-fanalyzer` — гонять под нагрузкой
  (фаза 4+).

### Сохранённые метрики (замерено в фазе 4, см. таблицу выше)
- RPS h2 vs h1.1 на тех же хендлерах: при достаточном числе воркеров h2
  выигрывает 87% за счёт мультиплексирования; на одном насыщенном воркере
  проигрывает 21%. Замер без указания `workers/threads` бессмыслен.
- Память на долгоживущем соединении: роста нет на 250 000+ потоков.

> ⚠️ Проверяйте, что Debug-сборка действительно санитайзерная:
> `-fsanitize`/`-fanalyzer` добавляются только при непустом `CMAKE_BUILD_TYPE`
> (`backend/CMakeLists.txt:14`). Пустой `CMAKE_BUILD_TYPE` в кеше даёт тихий
> false negative — сборка проходит, предупреждений нет, ASan не работает.
> Быстрая проверка: `nm -D exec/cwfr | grep -c __asan` должно быть > 0.

> ⚠️ **Замеры памяти под ASan гоняйте с
> `ASAN_OPTIONS=detect_stack_use_after_return=0`.** Иначе Debug-сборка на
> холостом ходу (ноль запросов, ноль соединений) даёт ровный линейный рост RSS
> ~4.5 КБ/с (~16 МБ/ч) — это не утечка, а fake stack детектора
> use-after-return: он включён по умолчанию, выделяет на поток регион ~11 МБ и
> раздаёт кадры round-robin, поэтому страницы подкачиваются постепенно. Рост
> ограничен размером этих регионов (≈11 МБ × число потоков + 1/8 на shadow);
> Release и несанитайзерные сборки на простое ровные.
>
> Как отличить артефакт от настоящей утечки: `ASAN_OPTIONS=print_stats=1` даёт
> **одинаковые** счётчики malloc/free на 15-й и 150-й секунде простоя (реальная
> утечка аллоцирует), LSan при выходе молчит, `strace -c` не показывает новых
> `mmap`/`brk` — растут только уже отображённые анонимные регионы. С
> `detect_stack_use_after_return=0` рост исчезает.

## Риски и митигации

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Баги HPACK → COMPRESSION_ERROR у реальных клиентов | высокая | критическое | Фаза 1 изолирована; тест-векторы RFC; `h2spec`; таблицы из стандарта дословно |
| Дедлок в блокировках (outbox/streams/fc/stream) | средняя | критическое | Жёсткий порядок захвата (`06` §2); ASan/TSan; стресс-нагрузка |
| Зависание больших ответов (flow control) | средняя | высокое | Авто-WINDOW_UPDATE на приёме; тесты с большими телами |
| Утечка `h2stream_t` (не освобождается) | средняя | среднее | Refcount; soak-тест; LSan; CLOSED→free с задержкой |
| Поломка горячего пути HTTP/1.1 | низкая | критическое | h2 использует **свой** read-буфер, общий scratch не трогает; регресс-тесты каждый PR |
| CONTINUATION-атака (огромные заголовки через множество CONTINUATION) | средняя | высокое | Лимит `max_header_list_size` + счётчик CONTINUATION на блок → PROTOCOL_ERROR при превышении |
| Несовместимость с какими-то клиентами | средняя | среднее | Тестировать против curl/nghttp/браузеров на каждой фазе |
| Решение «своё vs nghttp2» принято неверно → переделка | средняя | высокое | Принять осознанно ДО фазы 1 (`00` §2) |

## Решения, требующие подтверждения

1. **Своя реализация vs `nghttp2`.** Рекомендация: своё (соответствие этиосу +
   контроль над LT-epoll), таблицы HPACK из RFC. Пересмотреть, если фаза 1/3
   покажут неприемлемый объём работы.
2. **`PRIORITY`-фреймы (deprecated в RFC 9113).** Принять и игнорировать
   (безопасно) vs отвергать (RFC §6.3 рекомендует). Рекомендация: игнорировать
   ради совместимости со старыми клиентами.
3. ✅ **Решено: не делаем.** Server Push был реализован и удалён — исходная
   рекомендация «отложить/не делать, если нет конкретного сценария»
   подтвердилась. Причины и порядок восстановления — в разделе фазы 7.
4. **h2c.** Оба пути (prior-knowledge + Upgrade) или только prior-knowledge.
   Рекомендация: сначала prior-knowledge (фаза 6), Upgrade — по запросу.
5. ✅ **Сделано (хвост фазы 4).** Порядок оказался ровно рекомендованным:
   фиксированные окна в фазе 4, авто-масштаб — позже и по замерам. Числа,
   стенд и грабли — в разделе «Авто-масштабирование recv-окна».
6. **Сore: вынести в подмодуль отдельной веткой/PR по фазам** или
   фича-ветка на весь цикл. Рекомендация: фича-ветка `feature/http2`, сливать
   по фазам.
7. ✅ **Снято фазой 3.** Гейт `http2.enabled` вводить не требуется: h2,
   рекламируемый по ALPN, теперь обслуживается полноценно. Флаг может
   понадобиться позже как эксплуатационный «рубильник», но это не блокер.
8. ✅ **Сделано (2026-08-02).** `SSL_CTX_set_ciphersuites` добавлен, поле
   `ciphers` разбирается на 1.2/1.3 токены. Детали — в фазе 0, п. 4 и в
   `04` §«TLS 1.3 ciphers».
