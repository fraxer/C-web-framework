# HTTP/2 — Обзор плана внедрения

> Статус: черновик плана. Все ссылки на файлы/строки актуальны на момент разведки
> кодовой базы (ветка `master`, ядро `backend/core/`).

Этот документ — точка входа. Конкретика разнесена по файлам `01`…`07` в этом же
каталоге.

---

## 1. Цель

Добавить в фреймворк `cwfr` полноценную серверную поддержку **HTTP/2 (RFC 9113,
ранее RFC 7540)** с сохранением:

- существующего API хендлеров (`httpctx_t*` — без изменений);
- event-driven модели (epoll, SO_REUSEPORT, пул потоков-обработчиков);
- принципа «минимум внешних зависимостей» (всё своё — JSON, SHA, JWT, base64…).

Поддерживаются два транспорта:
- **h2** — HTTP/2 поверх TLS через **ALPN** (основной путь);
- **h2c** — HTTP/2 поверх открытого текста (upgrade / prior-knowledge), для
  внутреннего/DevOps-трафика.

---

## 2. Ключевое архитектурное решение (требует подтверждения)

**Писать протокол с нуля или использовать библиотеку `nghttp2`?**

`nghttp2` — эталонная C-библиотека HTTP/2 (MIT), используется в curl/Node/и т.д.
Она закрывает HPACK, фрейминг, потоки, flow control — почти всё, кроме I/O.

| Аспект | Своё (hand-rolled) | `nghttp2` |
|---|---|---|
| Соответствие этиосу репо (всё своё) | ✅ | ❌ новая большая зависимость |
| Риск багов интероперабельности | высокий | низкий (battle-tested) |
| Объём работы | очень большой | средний (только интеграция I/O) |
| Контроль над интеграцией с epoll | полный | callback-модель `nghttp2` неудобна под LT-epoll |
| Лицензия | своя (согласно `LICENSE`) | MIT — совместимо |

**Рекомендация:** писать **своими силами**, по образцу уже существующего
`websocketsparser` (он доказывает, что команда владеет возобновляемыми
фрейм-парсерами). Это сохраняет единообразие кодовой базы и прямой контроль над
событийным циклом. Исключение — **таблицы Хаффмана и static table из HPACK
брать дословно из RFC 7541** (это данные, а не логика: их невозможно «написать
неправильно», если копировать из стандарта).

См. также альтернативу и риски в `07-roadmap-testing.md`, § «Решения».

> ⚠️ Это решение нужно принять ДО старта. От него зависит объём всех фаз.

## 3. Что НЕ меняется

- **Хендлеры и middleware** — ноль изменений. Они по-прежнему получают
  `httpctx_t*` и вызывают `send_data/send_json/send_model/send_file/…`. HTTP/2
  становится «прозрачным» транспортом.
- **Роутинг, модели ORM, сессии, storage, i18n** — без изменений.
- **TLS-слой по цифрам** — минимальная версия TLS 1.2 уже выставлена
  (`openssl.c:62`), что соответствует требованию HTTP/2. SNI уже реализован
  и срабатывает **до** ALPN — композиция per-host протоколов достаётся бесплатно.

---

## 4. Что меняется / добавляется (дельты)

1. **Потоковая таблица (stream table).** Сейчас на соединение — ровно один
   `parser`/`request`/`response` (`connection_s.h:41-44`). HTTP/2 требует N
   параллельных потоков на одном TCP-соединении. → `h2session_t` + `hashmap`
   потоков. [Подробнее — `01-architecture.md`]
2. **Пер-соединениевый read-буфер.** Сейчас все соединения воркера делят один
   общий 16 KB scratch (`multiplexingserver.c:9,28`). Для интерливинга/разбиения
   фреймов это небезопасно → HTTP/2-сессии нужен собственный буфер. [`01`]
3. **ALPN.** Полностью отсутствует (`SSL_CTX_set_alpn_select_cb` нигде не
   вызывается). → добавить на каждый серверный `SSL_CTX`, ветвление h2/h1.1
   после хендшейка в `httpserverhandlers.c:682`. [`04-tls-alpn-h2c.md`]
4. **Исправление SSL I/O.** `__read`/`__wr` проверяют `errno`, а нужно
   `SSL_get_error` — иначе `SSL_ERROR_WANT_READ/WRITE` интерпретируются как
   ошибки. Обязательно для мультиплексированного h2. [`04`]
5. **Таймеры.** Их нет вообще (только TCP-keepalive). Нужны PING/idle/GOAWAY.
   → `timerfd` на воркер в том же epoll. [`06-lifecycle-concurrency-timers.md`]
6. **HPACK.** Новый подмодуль (Huffman + static/dynamic table). [`02-hpack.md`]
7. **Фрейм-уровень + конечный автомат потоков + flow control.** [`03-…`]
8. **Конкурентность.** Сейчас один спинлок `ctx->locked` на соединение. Для h2
   нужны потоковые блокировки + сериализатор записи. [`06`]

## 7. Главные риски (кратко)

- **HPACK-интероперабельность** — самая «нервная» часть; валидировать `h2spec`.
- **Конкурентность записи** — N потоков пишут HEADERS/DATA в один сокет;
  нужна бездеадлокная модель. Образец — `src/broadcast/broadcast.c` (очередь +
  батчинг).
- **Изменение read-буфера** — затрагивает горячий путь HTTP/1.1; нельзя ломать.
- **HEADERS с `END_HEADERS` через CONTINUATION** и пустые/нулевые блоки —
  типичный источник багов; покрывать тестами из RFC.
- **Flow control deadlock** — если не enlargать окна, large-response зависает.

Подробности и митигации — в `07-roadmap-testing.md`.
