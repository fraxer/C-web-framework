# Горячая перезагрузка

Горячая перезагрузка позволяет обновить конфигурацию без остановки сервера и
прерывания обработки запросов. По сигналу `SIGUSR1` сервер перечитывает
`config.json` и заново инициализирует компоненты: маршруты, домены и редиректы,
подключения к базам данных, хранилища, сессии, ограничители частоты, TLS и
планировщик задач.

## Что перезагрузка обновляет, а что нет

Перезагрузка перечитывает **конфигурацию**, а не код. Разница существеннее, чем
кажется:

| | Подхватывается по `SIGUSR1` |
|---|---|
| Любое значение в `config.json` | да |
| Маршрут, привязанный к другому `.so` или другой функции | да |
| `.so` по пути, который ещё не загружался | да |
| **Код уже загруженного `.so`** — обработчика или модуля приложения | **нет** |
| Бинарник `cwfr`, то есть само ядро | нет |

::: warning Пересобрать `.so` на месте недостаточно
Пересобрали обработчик или модуль приложения поверх прежнего файла, отправили
`SIGUSR1` — в процессе останется **прежний код**, и сколько сигналов ни посылай,
это не изменится. Нужен рестарт сервера.
:::

Причин две, и они разные. Модуль приложения из [`main.modules`](/config#modules)
не выгружается никогда: старые рабочие потоки в момент перезагрузки могут исполнять
его middleware, а зарегистрированные указатели на функции ведут внутрь его кода —
снять отображение значит выдернуть код из-под работающего потока. Обработчики
выгружаются, но новое поколение конфигурации загружает их **раньше**, чем
освобождается старое, поэтому счётчик ссылок никогда не падает до нуля и `dlopen()`
возвращает уже отображённый объект вместо чтения файла заново.

### Обновление кода без рестарта

Раз ограничение касается только **уже загруженного пути**, обойти его можно
версионированными именами файлов: класть новую сборку рядом под новым именем и
менять путь в конфигурации.

```json
"/api/users": {
    "GET": { "file": "handlers/models/lib_modeluser.2.so", "function": "list" }
}
```

Такой путь ещё не загружен, поэтому перезагрузка возьмёт новый файл. Со старым
`.so` это не работает — там имя то же самое.

С модулем приложения приём работает точно так же: укажите в `main.modules` новый
путь, и перезагрузка загрузит новый `.so`, а его `app_init()` заполнит только что
очищенный реестр middleware.

Оговорка одна: прежний модуль остаётся отображённым до конца жизни процесса —
выгрузить его, как сказано выше, нельзя. Многократная замена на лету поэтому
накапливает отображённую память, и рестарт рано или поздно всё равно нужен.

## Запуск перезагрузки

Событие перезагрузки привязано к сигналу `SIGUSR1`. Отправьте его процессу сервера
(`cwfr`) одним из способов:

```bash
pkill -USR1 cwfr        # по имени процесса
kill  -USR1 <pid>       # по PID процесса
```

Перед перезагрузкой сервер сбрасывает буферы логирования на диск, поэтому последние
записи не теряются.

## Проверка конфигурации

Новый `config.json` сначала парсится и валидируется. Если файл содержит ошибку или
невалидную конфигурацию — перезагрузка отменяется, а сервер продолжает работу со
старой конфигурацией. Это позволяет править конфигурацию «вживую» без риска
остановить работающий сервер.

Повторные сигналы, пришедшие во время перезагрузки, игнорируются — новая
перезагрузка начнётся только после завершения текущей.

## Режимы перезагрузки

Поведение активных соединений при перезагрузке задаётся свойством `reload` в секции
`main` (см. [Конфигурация → reload](/config#reload)). Значение по умолчанию — `soft`.

```json
{
    "main": {
        "reload": "hard",
        ...
    },
    ...
}
```

### soft <Badge type="tip" text="по умолчанию"/>

Сервер перестаёт принимать **новые** соединения, но продолжает обслуживать уже
активные — они завершаются естественным путём: до конца запроса, по истечении
таймаута keep-alive или при закрытии соединения клиентом. Перезагрузка выполняется,
как только закрыто последнее активное соединение. Ни один находящийся в обработке
запрос не обрывается.

### hard

Сервер принудительно закрывает все сетевые соединения (`shutdown` сокетов) сразу
после получения сигнала, обрывая активные запросы. Перезагрузка выполняется
максимально быстро. Режим удобен, когда изменения нужно применить срочно, а потеря
текущих запросов допустима.
